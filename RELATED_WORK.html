§The design space at a glance

I.Ancestry and foundations

1 Worlds and the scoping of side effects

Worlds can only commit a child into its parent and explicitly deferred the reconciliation of sibling worlds to future work — Manikin makes that reconciliation its centerpiece, with a git-like merge whose per-object read/write intersection rule is precise enough to detect write skew and a rebase that semantically replays messages where snapshot-based systems can only diff state.

A related-work section should present Manikin as the completion of the Worlds program: Warth, Ohshima, Kaehler, and Kay made side-effect scope a first-class value with tracked reads and writes and a validated commit, and Manikin inherits that architecture directly (the author cites the VPRI paper as an influence). The decisive difference is reconciliation topology and granularity: Worlds validates only child-to-parent commits — every location read in the child must still hold its first-read value in the parent — at raw memory-slot granularity, and relegates sibling worlds to future work where losers are simply discarded; Manikin makes sibling reconciliation the core contribution via merge (empty write/write and read/write intersections, hence write-skew detection and SSI-grade serializability) and rebase (semantic message replay after which merge is guaranteed), at the granularity of typed identities and contract-checked message dispatches rather than slots. Against the subjectivity branch (Us, Korz, COP, Tanter's contextual values), the contrast is that those systems scope which behavior or value applies in a context but provide no commit, no dependency tracking, and no way to reconcile divergent contexts — Manikin scopes state versions and is entirely about reconciling them. Against the managed-time branch (Glitch, Programming with Managed Time), Manikin shares journaled, replayable state transitions but swaps fine-grained replay-until-consistent within one timeline for coarse-grained transactional forking across timelines; notably, McDirmid and Edwards explicitly call for 'branching speculative time' as the future of managed time, which Manikin concretely delivers. Against Concurrent Revisions, the nearest fork/merge system, Manikin makes the opposite trade: revisions' typed joins never fail but abandon serializability, while Manikin's merges can fail precisely so that serializability survives. Honesty requires noting what Manikin lacks relative to this thread: no formal semantics (Worlds formalizes lookup; Burckhardt and Leijen formalize revisions), no optimized implementation study, no liveness/user-facing evaluation (Glitch, subjunctive interfaces), and no behavioral variation mechanism.

Worlds: Controlling the Scope of Side Effects

Warth, Ohshima, Kaehler, Kay · ECOOP 2011 (LNCS 6813, pp. 179-203); also VPRI TR-2011-001 · 2011

Manikin's named direct ancestor: first-class worlds are sprouted from a parent, every slot read or written in a world is tracked, and commit is guarded by what the authors call a serializability check — a commit from w_child to w_parent succeeds only if every location read in w_child still holds, in w_parent, the value it had when w_child first read it (otherwise CommitFailed), alongside a 'no surprises' isolation property. The paper formalizes property-lookup semantics, gives an efficient Squeak implementation, and demonstrates side-effect-rolling-back exception handling, multi-level undo for free, scoped extension methods in JS, a tree-undo bitmap editor, and OMeta backtracking. Crucially, the only reconciliation operation is child-to-parent commit; sibling worlds appear solely in future work, as racing 'experiments' where the first finisher propagates and the rest are discarded — merging siblings is left open. Manikin fills exactly that gap with symmetric merge (requiring empty write/write and read/write intersections, hence write-skew detection) and rebase (semantic replay from the common ancestor), while lifting granularity from raw memory slots to typed identities receiving contract-checked messages; unlike Worlds, Manikin has no formal semantics or optimized-VM implementation study.

Experimenting with Programming Languages

Warth · PhD dissertation, University of California, Los Angeles (also VPRI TR-2008-003) · 2009

The dissertation (title page 2009; also circulated as VPRI TR-2008-003) contains the original presentation of worlds together with OMeta, and frames both as infrastructure for 'programming via experiments' — tentatively doing, then undoing — which is the same experimentation stance Manikin operationalizes with cheap world forking. It contains material the ECOOP paper omits, notably Section 4.4.4 ('Scoping Methods, not Side Effects'), which confronts side-effectful extension methods in a worlds-based module: because a module-world captures all side effects, a mutating method's writes stay trapped in the module, and the dissertation's workaround is 'world-bound' setter methods that close over the top-level world — a fix it admits is clunky and interacts badly with worlds-based undo. Manikin departs from it in the same ways it departs from the ECOOP paper: sibling merge/rebase, message-level granularity, and contracts, none of which appear in the dissertation.

A Simple and Unifying Approach to Subjective Objects

Smith, Ungar · Theory and Practice of Object Systems (TAPOS) 2(3), pp. 161-178 · 1996

Us extends Self so that an object's state and behavior are a function of the perspective (layer) from which it is viewed, making layers first-class contexts for evaluating expressions. The Worlds paper explicitly identifies Us layers as 'very similar to worlds' minus the commit operation, so Us is Manikin's grandparent: perspective-relative object state without any reconciliation semantics. Manikin keeps the many-views-of-one-identity idea (an Id read through different worlds yields different versions) but makes reconciliation — validated commit, sibling merge, rebase — the centerpiece; conversely, Manikin has no subjective behavioral dispatch: the same message code runs in every world.

Korz: Simple, Symmetric, Subjective, Context-Oriented Programming

Ungar, Ossher, Kimelman · Onward! 2014, pp. 113-131 · 2014

Korz modernizes Us by combining implicit context dimensions with symmetric multiple dispatch over a sea of slots, so 'objects' are assembled subjectively from whatever slots pertain in the current context, with no layers or aspects. It shows the subjective-objects line evolving toward richer context selection, but context in Korz selects which slots/behavior apply — there is no isolation of side effects, no read/write tracking, and no commit or merge between contexts. Manikin is the complementary design: a single objective behavior definition whose state varies across worlds that can be transactionally reconciled, rather than behavior that varies across simultaneous context dimensions.

Context-oriented Programming

Hirschfeld, Costanza, Nierstrasz · Journal of Object Technology 7(3), pp. 125-151 · 2008

The COP manifesto: layers group behavioral variations that are activated and deactivated dynamically, scoping which method variants execute within a dynamic extent. It shares with Manikin the move of making 'scope' a first-class, programmer-controlled dimension, but COP scopes behavior while worlds-style systems scope state — a COP layer changes which code runs, whereas a Manikin world changes which version of the store is visible. COP systems provide no dependency tracking or conflict detection between layer activations; Manikin provides exactly that for state but offers no mechanism for behavioral variation.

Contextual values

Tanter · Dynamic Languages Symposium (DLS) 2008 · 2008

Tanter's contextual values are cells whose contents depend on the context in which they are read or written, and he shows they subsume a scoped-assignment construct that confines side effects to a dynamic extent — with any runtime value usable as a context, making it strictly more general than worlds as a scoping mechanism. The Worlds paper's own comparison applies equally to Manikin: contextual values have no commit, so scoped effects can never be validated and propagated, and overlapping non-exclusive contexts make the store hard to reason about. Manikin trades that generality for a strict world tree/DAG with precise per-dispatch read/write sets, which is what makes validated commit, merge, and rebase definable at all.

Concurrent Programming with Revisions and Isolation Types

Burckhardt, Baldassin, Leijen · OOPSLA 2010, pp. 691-707 · 2010

Concurrent Revisions is the closest contemporaneous fork/join design: tasks fork revisions of shared state and join them back, with per-datum isolation types (versioned, cumulative) whose declared merge functions resolve conflicts deterministically — join never fails, and the model deliberately abandons serializability in favor of a weaker, reasoned-about-directly guarantee; the Worlds paper itself criticizes rjoin for not detecting read-write conflicts. Manikin takes the opposite bet from the same git-like premise: merge(w1,w2) fails unless write/write and read/write intersections are empty, preserving serializable (SSI-grade) semantics, and reconciliation on conflict is done by rebase — semantically replaying messages — rather than by per-type merge functions. Manikin also merges arbitrary sibling worlds outside any structured fork/join discipline, but lacks Concurrent Revisions' determinism guarantee and formal semantics (Burckhardt and Leijen, ESOP 2011).

Usable Live Programming

McDirmid · Onward! 2013, pp. 53-62 · 2013

Presents Glitch-based live programming where probes and navigable execution traces give continuous feedback during editing; underneath, Glitch logs the imperative operations of each execution node so nodes can be re-executed when code or input changes, with logged operations automatically undone if not re-performed, requiring updates to be commutative and undoable. This is the 'tape/journal-based state' design point in the briefing: like Manikin, effects are recorded and computation is replayable, but the log serves incremental re-execution within a single evolving timeline rather than isolation. Manikin's rebase is a coarse-grained relative of Glitch replay (whole messages re-dispatched from a common ancestor, no commutativity requirement because merge validation orders them), while Manikin has nothing comparable to the live-editing experience.

Programming with Managed Time

McDirmid, Edwards · Onward! 2014, pp. 1-10 · 2014

The manifesto that time — the ordering and visibility of state updates — should be managed by the language just as memory is managed by GC, surveying FRP, STM, and similar systems and presenting Glitch, which replays tasks until consistent using commutative, rollback-able, logged updates. It cites the Worlds paper directly and proposes, as future managed time, 'branching speculative time' in which programmers explore multiple possible realities at once — a near-exact description of the design point Manikin occupies with forked immutable worlds. Manikin can be positioned as one concrete answer to that call, contributing validated sibling merge, write-skew detection, and contract checking, while lacking Glitch's fine-grained incremental consistency and liveness.

Subjunctive Interfaces: Extending Applications to Support Parallel Setup, Viewing and Control of Alternative Scenarios

Lunzer, Hornbæk · ACM Transactions on Computer-Human Interaction (TOCHI) 14(4), Article 17 · 2008

The HCI ancestor of the worlds idea (Lunzer is acknowledged in the Worlds paper): applications are extended so users can set up, view, and control multiple alternative scenarios side by side, with user studies showing higher satisfaction and lower workload — initial studies found no reduction in completion time, though a redesigned interface in a follow-up five-session study yielded roughly 27% faster task completion. It supplies the user-facing motivation — people naturally want coexisting what-if versions of application state — but implements alternatives ad hoc per application, with no general substrate, no dependency tracking, and no notion of reconciling divergent scenarios. Manikin's worlds with recorded read/write sets are precisely the semantic substrate on which subjunctive interfaces could be built soundly, including merging two explored scenarios, which subjunctive interfaces never attempt.

Enhancing JavaScript with Transactions

Dhawan, Shan, Ganapathy · ECOOP 2012 (LNCS 7313, pp. 383-408) · 2012

Transcript modifies SpiderMonkey so a host page can wrap untrusted guest JavaScript in transactions: guest actions are journaled and speculative, read/write sets are maintained, external effects suspend the transaction to the host, DOM updates are speculative, and the host introspects the journal to detect conflicts and commit or repair. The paper positions itself as 'most closely related to Worlds' in providing first-class primitives to contain side effects, making it a verified follow-up extending worlds toward transactions — but toward security mediation of a guest/host pair, not concurrency. Manikin shares the journaled, speculative, read/write-set machinery but points it at sibling-world merging, rebase, and design-by-contract, and stays a pure embedded library rather than a modified engine.

Stores and Partial Continuations as First-Class Objects in a Language and its Environment

Johnson, Duggan · POPL 1988, pp. 158-168 · 1988

The earliest ancestor the Worlds paper credits for first-class program stores: in the GL language the store is a value that can be captured and later restored (Morrisett's 1993 'Refining first-class stores' later partitioned it into separately restorable sub-stores). This lineage established state-as-value but through a save-and-restore interface over a single timeline, whereas worlds — and Manikin after them — let many store versions coexist as 'parallel universes'. Manikin pushes the same idea two steps further: stores are not only first-class and coexisting but carry semantic read/write dependency metadata per message dispatch, enabling merge validation no snapshot-based first-class store can express.

Multiverse Debugging: Non-Deterministic Debugging for Non-Deterministic Programs

Torres Lopez, Gurdeep Singh, Marr, Gonzalez Boix, Scholliers · ECOOP 2019 (LIPIcs 134, article 27) · 2019

Debugs nondeterministic actor programs by letting the debugger explore all forked execution paths of a program simultaneously — a multiverse of states rather than one trace. It is the debugging-side realization of Manikin’s “light model checking via forked worlds” claim, and evidence that first-class branching state has payoffs beyond concurrency control; Manikin could host exactly this debugger, with merge information the multiverse debugger lacks.

Practical Object-Oriented Back-in-Time Debugging

Lienhard, Gîrba, Nierstrasz · ECOOP 2008, pp. 592–615 (Distinguished Paper) · 2008

Makes omniscient debugging practical by keeping object history in the application heap so unreachable history is garbage-collected. It documents both the value and the cost of exactly what Manikin retains by design — every historical version of every object — and marks a payoff (asking any past state “who set this?”) that Manikin’s worlds support natively but its tooling does not yet surface.

2 Objects, values, and identity

Where Clojure's epochal time advances one identity at a time behind an STM, Manikin advances a whole immutable world per message dispatch — so application state can be forked, merged, and rebased like a git repository, with conflicts defined by recorded semantic read/write sets rather than by textual diffs.

This thread supplies the conceptual vocabulary that Manikin's "Worldly Objects" turn into mechanism. MacLennan's value/object dichotomy and Baker's egal equality identify exactly the two things Manikin separates: immutable state values versus identity, which Manikin reifies as a typed surrogate (Id[O]) in the sense of Khoshafian and Copeland. Reed's 1978 thesis and Clojure (Hickey) are the two prior systems in which an object IS a succession of immutable versions, so a related-work section must concede that Manikin's Pure Object = (Id, versioned states) is a rediscovery of that model rather than a new ontology; Manikin's novelty sits on top of it. Concretely, Manikin takes Cook's objects-versus-ADTs distinction seriously by making state a pure ADT-like value while restricting all interaction to Kay-style message sends, then wraps every message in a pre/app/eff/pst mini-transaction whose read and write sets (including reads performed inside contract checks) are recorded by the enclosing immutable World. That per-dispatch dependency footprint is what none of the prior identity models have: Reed serializes versions by globally assigned pseudo-time, Clojure advances epochal time one identity at a time behind an STM, and FRP indexes values by continuous time, whereas Manikin versions the entire world and can therefore fork, merge (rejecting write/write and read/write intersections, i.e. detecting write skew), and rebase application state like a git repository with semantic conflicts. What Manikin lacks relative to this thread: the formal type theory of Abadi and Cardelli, a single language-level equality story like egal, and the asymptotically efficient persistence machinery of Driscoll et al.

On Understanding Data Abstraction, Revisited

William R. Cook · OOPSLA 2009 · 2009

Cook's essay (explicitly cited by Manikin) separates abstract data types (hidden representation, extensional operations over it) from objects (autognostic procedural abstractions known only through their interface). Manikin deliberately straddles the dichotomy: an object's state is a plain immutable value with a known representation (ADT side), while all interaction is forced through Message dispatch to an Id via a World (object side), so behavior and state are kept in separate immutable values. Cook offers no account of state change over time or transactions; Manikin adds the 4-stage pre/app/eff/pst message protocol and world-level read/write tracking on top of Cook's distinction. Conversely, Manikin has none of the interface-polymorphism/subtyping analysis that is the essay's core.

Equal Rights for Functional Objects or, The More Things Change, The More They Are the Same

Henry G. Baker · ACM OOPS Messenger 4(4), pp. 2-27 · 1993

Baker argues that object identity is operationally meaningful only under side effects, so immutable ('functional') objects deserve extensional value equality, and proposes the single egal predicate (address comparison for mutables, structural for immutables). Manikin agrees with the diagnosis but resolves it structurally rather than via an equality predicate: states are always immutable values compared extensionally, and 'sameness over time' is exiled into an explicit typed surrogate Id[O] plus a world-maintained version chain. Baker wanted one equality operator inside a mutable language; Manikin removes mutation from objects entirely, so egal degenerates to value equality plus identity equality on Ids. The lineage is direct: Clojure's = adopts egal (per Hickey's HOPL paper), and Manikin inherits the same value semantics transitively.

Values and Objects in Programming Languages

Bruce J. MacLennan · ACM SIGPLAN Notices 17(12), pp. 70-79 · 1982

The earliest sharp statement of the dichotomy Manikin is built on: values are timeless abstractions for which updating and sharing are meaningless, while objects exist in time and are created, shared, and updated. Manikin operationalizes the essay: what MacLennan calls an object is decomposed into an Id plus a time-ordered succession of MacLennan-style values inside a World, so 'update' becomes appending a new value at an identity. MacLennan's paper is purely conceptual with no mechanism; Manikin adds the transactional message protocol, contracts, and per-dispatch dependency recording. Nothing in Manikin contradicts the essay — it is close to a direct implementation of its recommendation that languages discriminate the two notions.

Object Identity

Setrag N. Khoshafian, George P. Copeland · OOPSLA 1986, pp. 406-416 · 1986

Defines the classic continuum of identity support and advocates surrogates: system-generated identifiers fully independent of an object's state, location, and addressability, strong enough to support temporal models that retain past versions. Manikin's Id[O] is precisely a typed surrogate (with an init factory for pristine state), and its worlds realize the paper's 'identity through change' with every historical id:version retained. Khoshafian and Copeland also analyze identity-aware operations (identical vs. equal predicates, shallow/deep copy and merge) in a database data model; Manikin replaces that operation set with message dispatch plus world-level merge/rebase driven by recorded read/write sets. What Manikin adds beyond the paper is the transactional semantics attached to each state transition; what it drops is the paper's concern for identity under physical data independence in a DBMS.

Naming and Synchronization in a Decentralized Computer System

David P. Reed · MIT PhD thesis, MIT/LCS/TR-205 · 1978

Reed's NAMOS model is, to our knowledge, the earliest full system in which an object is a named sequence of immutable versions: references always select a version by pseudo-time, and atomic actions group tentative new versions that commit or abort together, yielding multiversion timestamp concurrency control. Manikin shares the ontology exactly — identity plus immutable version history, transactions that append versions, reads from consistent snapshots — four decades later at the level of an embedded application DSL. The concurrency mechanism differs fundamentally: Reed serializes by globally assigned pseudo-times in a distributed OS, whereas Manikin forks whole immutable worlds and merges them with explicit write/write and read/write intersection tests (detecting write skew, SSI-grade) plus a semantic rebase-replay slow path, none of which exists in Reed's timestamp scheme. Manikin lacks Reed's treatment of decentralized naming and network failure.

The Early History of Smalltalk

Alan C. Kay · HOPL-II (ACM SIGPLAN Notices 28(3), pp. 69-95) · 1993

Kay's retrospective fixes the original framing of OOP as messaging, local retention and protection of state, and extreme late binding — famously insisting the big idea is messaging, not objects. Manikin is radically faithful to the messaging half: the only way to touch an object is to dispatch an immutable Message value to its Id, and even side effects (eff) are defined as sending further messages to other objects. It departs from Kay on everything else: messages are statically typed 4-stage mini-transactions over immutable state rather than late-bound imperative sends, and encapsulated mutable state is replaced by world-versioned values. Manikin thus keeps Kay's interaction discipline while discarding the dynamism that Kay considered essential.

A Theory of Objects

Martín Abadi, Luca Cardelli · Springer, Monographs in Computer Science · 1996

The standard formal foundation for objects: object calculi with method invocation and method update as primitives, in both functional variants (where update returns a new object, as in the ς-calculus) and imperative ones, with full type systems covering self, subtyping, and variance. The functional calculi's update-returns-new-object is the same move as Manikin's app stage producing a new state value, but Abadi-Cardelli objects are anonymous method suites with no global identity, so the 'new object' severs continuity that Manikin preserves via Id plus world version chains. Manikin adds transactional messaging, cross-object contracts, and multi-world concurrency, none of which the calculi model; it lacks any comparable metatheory. (The briefing's tentative citation 'A Theory of Substructural Types...' as immutable-object literature appears to be a misremembering — the only real match, Tov and Pucella's 'A Theory of Substructural Types and Control' (OOPSLA 2011), concerns linear/affine references and control effects, not object identity, so it is omitted.)

The Value of Values

Rich Hickey · industrial keynote (JaxConf 2012; long version GOTO Copenhagen 2012) · 2012

Hickey's influential industrial argument against place-oriented programming: facts are immutable values, 'update' means accreting new facts, and systems (exemplified by Datomic, where the database is itself an expanding immutable value with queryable history) should never overwrite. Manikin's worlds embody the same accretion discipline — every id:version is retained and successful dispatches append to a built-in event log, giving Datomic-style as-of history inside an embedded DSL. The difference is the concurrency story: Datomic funnels all writes through a single serializing transactor, while Manikin lets applications fork worlds concurrently and merge them under precise read/write-set checks, with rebase as the recovery path. As a talk it provides motivation and vocabulary, not mechanism; the HOPL IV paper is the citable companion.

Functional Reactive Animation

Conal Elliott, Paul Hudak · ICFP 1997, pp. 263-273 · 1997

Fran introduced behaviors — first-class time-varying values, denotationally Time -> a — and events, founding FRP; a behavior is in effect an identity whose observed values are immutable and indexed by continuous time. This is the FRP analogue of the identity-as-succession-of-values idea: like Manikin, no observation ever sees a mutated value, only a different value at a different time. But FRP's time is continuous, dataflow-driven, and composed by combinators, whereas Manikin's 'time' is the discrete per-world sequence of message dispatches with explicit transactional boundaries, contracts, and recorded dependencies. Manikin has no declarative temporal composition (integration, switching) and FRP has no transactions or fork/merge, so the two occupy disjoint corners of the same value-over-time design space.

Making Data Structures Persistent

James R. Driscoll, Neil Sarnak, Daniel D. Sleator, Robert E. Tarjan · Journal of Computer and System Sciences 38(1), pp. 86-124 · 1989

The foundational algorithms paper on persistence: fat-node and node-copying techniques that make ephemeral linked structures partially or fully persistent with O(1) amortized space per update, so every historical version stays accessible. Manikin's worlds demand exactly full persistence at the object-graph level — every id:version of every object is kept — but the reference implementations realize it naively via per-world maps rather than with these asymptotically optimal techniques, so the paper marks what Manikin's version retention costs and how it could be engineered down. Note also that Manikin's world merge corresponds to the strictly harder confluent persistence (combining two versions), which this paper explicitly leaves out and later work (e.g. Fiat and Kaplan) formalizes. The paper contributes no identity or transaction semantics; it is infrastructure for this thread, not a competing model.

Purely Functional Data Structures

Okasaki · Cambridge University Press (book; CMU PhD thesis 1996) · 1998

The canon of persistence achieved functionally — amortized analysis with lazy evaluation, and the design catalogue every immutable-collections library (including the JVM structures Manikin’s worlds sit on) descends from. Driscoll et al. give the imperative persistence machinery; Okasaki gives the functional one Manikin actually uses. 3 Monads, effects, and the “inverse of a monad”

where the monadic tradition makes effects explicit in types and invisible at run time, Manikin makes them invisible in types and exhaustively recorded at run time — a World is a reified trace of precisely the dependency information that effect and coeffect systems approximate statically.

This thread splits into two branches of the same problem — reconciling pure semantics with imperative ergonomics — and Manikin deliberately takes the minority branch. The majority branch (Moggi, Wadler, IO/ST, monad transformers, Koka's effect rows) makes effects visible in types and threads them explicitly; Manikin's author explicitly rejects it, calling his alternative "the inverse of a monad": a mutable Environment hidden in a ThreadLocal lets business logic read object state and send messages in direct style, while an immutable World value is still threaded purely underneath by the runtime. The closest formal accounts of that pattern are Filinski's monadic reflection (direct-style code whose meaning is a monadic computation) and Plotkin–Pretnar handlers (effects as operations given meaning by a dynamically scoped interpreter — exactly what Manikin's swap-in World implementations do for event sourcing, mocking, model checking, and CockroachDB-backed distribution), with Lewis et al.'s implicit parameters supplying the dynamic-scoping-under-static-types lineage that Scala's own context functions descend from. What Manikin adds that no work in this thread has: the effect trace is reified — each dispatch's exact read and write sets (including reads inside pre/post conditions) are recorded per immutable World version and then used transactionally, so forked worlds merge iff write/write and read/write intersections are empty (detecting write skew) and rebase by semantic replay; effect information becomes a concurrency-control and versioning mechanism rather than a typing discipline. What Manikin lacks, measured against this thread, is every static guarantee the branch it rejected provides: no parametricity fence like runST to stop state escaping the Environment's dynamic extent, no effect rows or handler types, no capture checking — safety is architectural and dynamic, and nothing but convention stops a leaked object reference from outliving its world. Notions of computation and monads

Moggi · Information and Computation 93(1) · 1991

Moggi's paper is the semantic foundation of the whole thread: a notion of computation (state, exceptions, nondeterminism) is a monad T, and effectful programs are arrows in its Kleisli category. Manikin lives in exactly this design space — dispatching a Message threads an immutable World through every step, which is the state-monad discipline in all but syntax — but it refuses to surface T in user code, hiding the threading behind a ThreadLocal Environment. Manikin also records structure Moggi's framework does not: per-dispatch read/write sets and a pre/app/eff/pst transaction shape, used later for merging forked worlds rather than for typing.

Monads for functional programming

Wadler · Advanced Functional Programming (Båstad Spring School), LNCS 925, Springer · 1995

Wadler turned Moggi's semantics into a programming technique, showing how monads structure evaluators, in-place-update arrays, and parsers with explicit bind. This is the ergonomic regime Manikin's author explicitly rejects: in Manikin, business logic (pre/app/eff/pst bodies) reads imperatively — obj.balance, send(...) — with no bind or for-comprehension, because the World is threaded by the runtime, not the programmer. The trade is deliberate: Wadler's style makes effect plumbing visible and checkable in types; Manikin's makes it invisible in source but dynamically recorded in the World's read/write sets.

Imperative functional programming

Peyton Jones, Wadler · POPL 1993 · 1993

This paper introduced monadic I/O: real-world effects confined to an IO type so the rest of the language stays pure. Manikin shares the containment strategy — its eff stage may only send messages to other objects, and genuinely external interaction is pushed into World implementations, one boundary just as IO is. The difference is that IO actions are opaque and unreplayable once run, whereas every Manikin dispatch is appended to an event log with all historical object versions retained, so effects can be inspected, replayed (rebase), and merged after the fact.

Lazy Functional State Threads

Launchbury, Peyton Jones · PLDI 1994 · 1994

runST encapsulates genuinely mutable state behind a pure interface, with a rank-2 type ensuring by parametricity that no reference escapes the state thread. This is the closest typed ancestor of Manikin's Environment trick: both let imperative-looking code manipulate state while the enclosing computation remains observably pure. But the guarantees are opposite in kind — runST's fence is static and its state is ephemeral (destroyed at exit), while Manikin's fence is merely architectural (nothing in the JVM type system stops the ThreadLocal Environment or an object reference from escaping) and its state is maximally persistent: every id:version survives, which is what makes fork/merge/rebase possible at all. Manikin lacks runST's escape guarantee; runST lacks any notion of history or mergeability.

Representing Monads

Filinski · POPL 1994 · 1994

Filinski proved that any definable monad can be represented in direct style using delimited continuations (shift/reset) plus a single mutable cell — monadic reflection: effectful-looking code whose meaning is a pure monadic computation. This is the closest formal account in the literature of Manikin's 'inverse of a monad': the ThreadLocal-carried Environment over immutable Worlds is an engineering realization of the same inversion on a platform without delimited control, letting direct-style reads and sends denote pure World-to-World functions. What Filinski has and Manikin lacks is the correctness theorem — Manikin offers no proved correspondence between its direct-style surface and the underlying pure World semantics, only the implementation invariant that Worlds are immutable.

Implicit parameters: dynamic scoping with static types

Lewis, Launchbury, Meijer, Shields · POPL 2000 · 2000

This paper gives the standard typed account of dynamically scoped variables: implicit parameters are inferred into types and bound by a dynamically scoped construct, reconciling Hindley-Milner with dynamic binding. Manikin's Environment is precisely such a dynamically scoped variable — the current World, installed for the dynamic extent of a dispatch — but realized untyped via JVM ThreadLocal, so its presence appears in no signature. Scala's implicits and context functions descend from this line and could type Manikin's Environment; the author declined that route for Java-core compatibility, forgoing the static tracking this paper shows is achievable.

Handlers of Algebraic Effects

Plotkin, Pretnar · ESOP 2009 (LNCS 5502; journal version "Handling Algebraic Effects", LMCS 2013) · 2009

Plotkin and Pretnar's handlers interpret effect operations at the nearest dynamically enclosing handler — effects as an interface, interpretation supplied by dynamic scope. Manikin's swap-in World implementations are exactly handler-shaped: the same business logic's operations (read object state, send message) receive different interpretations — in-memory, event-sourced, mock-injected, model-checked, or executed on CockroachDB — depending on which World the Environment carries at dispatch time. The differences: handlers are a typed language construct that can capture and resume continuations and be locally nested, whereas Manikin's Worlds are a coarse-grained OO interface installed per computation, with no continuation capture and no effect typing; conversely, no handler calculus records read/write sets or supports merging two divergent interpretations of history.

Programming with algebraic effects and handlers

Bauer, Pretnar · Journal of Logical and Algebraic Methods in Programming 84(1) · 2015

Eff is the first full language built around Plotkin-Pretnar handlers, with first-class effect instances (fresh mutable references, channels) created dynamically and handled as homomorphisms from free algebras. Eff's dynamically generated effect instances parallel Manikin's typed identities Id[O] — both name stateful resources at run time rather than in a static effect signature. Eff demonstrates at language level what Manikin does as a JVM library with a fixed operation vocabulary (read/send); Manikin adds what Eff has no analogue for: every handled computation leaves a versioned, event-logged trace whose read/write sets support serializable merge of forked runs.

Type directed compilation of row-typed algebraic effects

Leijen · POPL 2017 · 2017

Koka infers extensible effect rows for every function and compiles handlers efficiently via type-directed selective CPS — the static-typing endpoint of the effects spectrum, where a function's type conservatively over-approximates everything it might do. Manikin occupies the opposite endpoint: zero static effect information, with the exact read and write set of each dispatch (including reads performed inside pre- and postconditions) captured dynamically. That precision is load-bearing — merge(w1,w2) needs exact per-object sets to soundly detect write skew, which a row type's over-approximation could not decide — but the price is that Manikin can verify nothing before running, while Koka rejects effect-incorrect programs at compile time.

Effects as capabilities: effect handlers and lightweight effect polymorphism

Brachthäuser, Schuster, Ostermann · OOPSLA 2020 (PACMPL 4, article 126) · 2020

Effekt abandons effect rows for capability passing: an effect type records what a function demands from its calling context, and handlers introduce term-level capabilities that are second-class so they cannot escape their handler's dynamic extent. This is the closest typed formulation of Manikin's stance that effects are things the ambient context provides — Manikin's Environment is a single ambient capability granting world access, but untyped and first-class, so nothing enforces the non-escape property Effekt gets by construction. Effekt thus shows exactly what a statically safe Manikin surface would look like; Manikin in turn shows a use of the capability (transactional read/write recording, world forking) that Effekt's capabilities do not perform.

Coeffects: a calculus of context-dependent computation

Petricek, Orchard, Mycroft · ICFP 2014 · 2014

Petricek et al. dualize effect systems: indexed comonads statically track what a computation requires of its context — variable usage, resources, environment properties — rather than what it does to the world. Manikin's read set is a dynamic coeffect: precisely which object versions a dispatch consumed from its World, including reads made by pre/post condition checks. Where the coeffect calculus derives this demand information statically and uses it for typing, Manikin discovers it at run time and uses it operationally — merge succeeds iff read/write intersections between forked worlds are empty — a transactional application of context-dependence that coeffect systems do not address.

Capturing Types

Boruch-Gruszecki, Odersky, Lee, Lhoták, Brachthäuser · ACM Transactions on Programming Languages and Systems 45(4), article 21 · 2023

The formal core of Scala 3's capture checking (the caprese project): CC<:box tracks the free capabilities captured by values in types, enabling effect safety via scoped capabilities without effect rows. This is directly relevant to Manikin's principal soundness gap — the ThreadLocal Environment and the object views it hands out are invisible to Scala's current type system, so a reference can silently outlive its world's dynamic extent. A capture-checked Manikin frontend could make the Environment an explicit tracked capability and statically forbid such escapes, converting Manikin's architectural discipline into a machine-checked one; the paper postdates Manikin's development (~2018-2021), which explains why the library relies on convention instead.

Extensible effects: an alternative to monad transformers

Kiselyov, Sabry, Swords · ACM SIGPLAN Haskell Symposium 2013 · 2013

Kiselyov, Sabry, and Swords document the engineering failure mode of monad transformer stacks — rigid static ordering, quadratic lifting — and replace them with one Eff monad over an open union of effects, interpreted by dynamically located handlers ('interpreters as dynamically requested authorities'). Their diagnosis is the strongest in-tradition support for Manikin's decision to reject monads outright: if transformer composition is painful even in Haskell, it is prohibitive in a Java-core embedded DSL. But their remedy stays typed and pure while Manikin's does not — Manikin buys direct-style ergonomics with an untyped ThreadLocal, gaining in exchange the recorded read/write sets and world history that Eff's interpreters do not keep.

What Color is Your Function?

Nystrom · blog post, journal.stuffwithstuff.com (industrial) · 2015

Nystrom's essay is the canonical industrial statement of the function-coloring problem: once effectful (async) functions are marked in signatures, the marking propagates virally and bifurcates the ecosystem — the ergonomic cost that also afflicts monadic and row-typed effect signatures. Manikin's architecture is a direct answer on the colorless side: because the World travels in the ambient Environment rather than in types, message logic is uncolored and identical business code runs under in-memory, event-sourced, model-checking, or distributed CockroachDB worlds. The cost is the mirror image of Nystrom's complaint: with no color anywhere, callers cannot tell pure code from world-touching code, a distinction every typed system in this thread preserves.

Simplicitly: Foundations and Applications of Implicit Function Types

Odersky, Blanvillain, Liu, Biboudis, Miller, Stucki · POPL 2018 (PACMPL 2(POPL), article 42) · 2018

Gives Scala’s implicit parameters and implicit function types a foundation (the SI calculus) and shows context propagation without monadic plumbing — the typed, principled version of “context without monads,” in Manikin’s own host language. 4 State-centric application architectures added in the completeness pass

Redux gave one immutable store an action log and time-travel; Manikin gives every store a version graph — Redux replays one timeline, Manikin merges several.

The mainstream incarnation of Manikin’s own architecture arrived by a different road. “Out of the Tar Pit” supplied the manifesto — complexity is caused by mutable state, so hold essential state immutably and derive the rest — and the Elm/Redux line turned a restricted form of that stance into the dominant front-end pattern: one immutable store, advanced only by dispatching immutable action values through a pure update function, with an action log that enables time-travel debugging by replay. A single Manikin world evolving under message dispatch is exactly this architecture generalized: typed identities instead of one anonymous store, messages that atomically span multiple objects, contracts on every dispatch, and — the part with no Redux analogue at all — forking, merging, and rebasing of divergent stores. Redux DevTools’ replay is the trivial linear case of rebase. Omitting this thread would read as unawareness of the paper’s own idea in industrial dress; including it supplies a familiar on-ramp for readers.

Out of the Tar Pit

Moseley, Marks · SPA 2006 (workshop paper) · 2006

The canonical complexity manifesto: most software complexity is accidental and flows from mutable state and uncontrolled order; the remedy is to hold essential state as immutable relations and derive everything else declaratively (functional relational programming). Manikin agrees on the diagnosis and on banishing in-place mutation, but keeps object identity and message dispatch where Moseley and Marks would dissolve objects into relations; its worlds give the essential-state/derived-state split a transactional and versioned form the essay never develops.

Asynchronous Functional Reactive Programming for GUIs

Czaplicki, Chong · PLDI 2013 · 2013

The Elm paper: a statically typed FRP language whose signals are eventually organized (in the folklore “Elm Architecture”) into a single immutable model advanced by a pure update function over typed messages. That model–update–message triple is a linear, single-object special case of Manikin’s world–dispatch–message triple; Manikin adds typed identities, multi-object atomic dispatch trees, contracts, and world fork/merge. Elm conversely offers a full reactive rendering story and static effect confinement that an embedded JVM DSL cannot.

Redux (single immutable store with action replay)

Abramov, Clark · industrial system (redux.js.org) · 2015

Redux froze the Elm Architecture into a JavaScript library: one store, pure reducers over an append-only action log, and time-travel debugging by replaying actions into past states. The action log is an event source and DevTools replay is exactly Manikin’s rebase restricted to one linear history. What Redux lacks defines Manikin’s delta: no typed identities (one monolithic state tree), no multi-object transaction boundaries, no contracts, no recorded read sets, and no notion of merging two divergent stores — concurrent Redux apps reconcile by ad-hoc means.

II.Transactions and concurrency

5 Software transactional memory

where an STM's read/write sets are scaffolding demolished the instant a transaction commits, Manikin makes them the permanent load-bearing structure of the world, turning transaction bookkeeping into version control.

Manikin's message dispatch is an optimistic mini-transaction in the direct lineage of STM: each dispatch records precise per-object read and write sets (including reads performed inside pre- and postconditions), and merge(w1,w2) applies the classic conflict test — empty write/write and read/write intersections — which is exactly the read-set validation of TL2 or JVSTM lifted to application-object granularity. The decisive difference is the lifetime and status of that bookkeeping: every STM in this thread treats read/write sets and old versions as ephemeral scaffolding, discarded at commit or abort (TL2, CCSTM) or garbage-collected as soon as no live transaction needs them (JVSTM, Clojure), whereas Manikin's worlds retain every id:version and the dependency sets of every committed dispatch forever, and that retention is precisely what makes old-state postconditions, built-in event sourcing, and git-like rebase expressible at all. Manikin also transacts at a different granularity: not arbitrary atomic blocks over words or refs, but typed messages with a pre/app/eff/pst contract structure, placing its conflict semantics closer to the method-level, commutativity-based view of transactional boosting than to word-level STM — except that Manikin derives conflicts automatically from recorded sets and needs no programmer-supplied inverses, because nothing is ever destructively updated. Against Clojure specifically, Manikin's automatic read-set tracking detects write skew that Clojure's snapshot-isolation STM only prevents under manual ensure calls. What Manikin lacks relative to this thread is equally clear: no retry/orElse-style blocking composition, no progress guarantees or contention management, and none of STM's performance engineering — its merge is an explicit application-level act and rebase replay is an acknowledged slow path, so it competes on semantics (auditable history, contracts, replay), not on synchronization throughput.

Transactional Memory: Architectural Support for Lock-Free Data Structures

Herlihy, Moss · ISCA 1993 (20th Annual International Symposium on Computer Architecture), pp. 289-300 · 1993

The founding TM paper: short optimistic transactions over multiple independently chosen memory words, with conflict detection piggybacked on cache coherence, as a replacement for locks. Manikin inherits the core move — optimistic execution plus read/write-set conflict detection instead of mutual exclusion — but relocates it from bounded hardware transactions over words to unbounded application-level transactions over typed object identities. Herlihy/Moss transactions leave no trace after commit; a Manikin dispatch leaves a permanent event-log entry, its dependency sets, and a new object version in the world.

Software Transactional Memory

Shavit, Touitou · PODC 1995 (14th ACM Symposium on Principles of Distributed Computing), pp. 204-213 · 1995

First software-only TM, coining the term: non-blocking multi-word atomic updates on stock hardware using load-linked/store-conditional, but restricted to static transactions whose data set is declared in advance. Manikin is likewise software-only but records its read/write sets fully dynamically — including reads that occur inside precondition and postcondition evaluation, a class of reads mainstream STMs do not track as first-class transactional metadata (Harris and Peyton Jones's invariant-checking extension being the nearest exception). Shavit/Touitou's helping-based lock-freedom addresses thread-level progress, a concern Manikin sidesteps entirely because forked worlds never contend on shared mutable state; conflicts surface only at explicit merge.

Software Transactional Memory for Dynamic-Sized Data Structures

Herlihy, Luchangco, Moir, Scherer III · PODC 2003 (22nd ACM Symposium on Principles of Distributed Computing), pp. 92-101 · 2003

DSTM introduced dynamic, object-granularity STM: transactions open TMObjects in READ or WRITE mode, writers clone the object so an old and new version coexist until commit, and obstruction-freedom plus pluggable contention managers govern progress. This is the closest granularity match to Manikin, whose app stage is likewise a pure old-version-to-new-version transition on a whole object and whose conflicts are detected per object identity, not per word. But DSTM's old versions exist only until commit resolution and its opened-object sets die with the transaction, whereas Manikin keeps every version and every dependency set as first-class world state; DSTM also offers nothing like pre/post contracts or replay.

Composable Memory Transactions

Harris, Marlow, Peyton Jones, Herlihy · PPoPP 2005 (10th ACM SIGPLAN Symposium on Principles and Practice of Parallel Programming), pp. 48-60 · 2005

STM Haskell showed that transactions compose when the type system confines them to pure, re-executable STM actions, and added the blocking combinators retry and orElse. Manikin depends on the same purity-for-re-executability bargain — app must be a pure state transition and eff may only send messages, which is exactly what makes rebase's semantic replay sound — but enforces it by convention and API shape rather than by a monadic type. Indeed Manikin explicitly rejects the monadic packaging, hiding a mutable Environment behind a ThreadLocal (the author's 'inverse of a monad') so business logic reads imperatively; the cost is losing STM Haskell's static effect guarantees and its retry/orElse composition, for which Manikin has no analogue.

Transactional Memory with Data Invariants

Harris, Peyton Jones · TRANSACT 2006 (1st ACM SIGPLAN Workshop on Languages, Compilers, and Hardware Support for Transactional Computing) · 2006

Extends STM Haskell with dynamically registered invariants ('check E') evaluated atomically at every commit, pinpointing exactly which atomic block breaks an invariant; a design section further sketches two-state predicates over state pairs via an 'old' combinator that runs a read-only computation against the pre-transactional state (e.g. 'this counter never decreases'), though the implemented extension checks single-state invariants. This is the nearest STM precedent for Manikin's pst stage, which likewise checks multi-object conditions with access to old state (e.g. the sum of two account balances is unchanged by a transfer). The differences: Harris/Peyton Jones invariants are global and checked against every subsequent commit, while Manikin's postconditions attach to a specific message type and run once per dispatch; and because Manikin's worlds retain full history, a postcondition's old-state reads are ordinary versioned reads that also enter the recorded read set and thus participate in merge conflict detection.

Transactional Locking II

Dice, Shalev, Shavit · DISC 2006 (20th International Symposium on Distributed Computing), LNCS 4167, pp. 194-208 · 2006

TL2 is the canonical high-performance STM algorithm: per-stripe version numbers, a global version clock, and commit-time read-set validation guaranteeing transactions only ever see consistent snapshots. Manikin's id:version pairs and merge check are structurally the same validation — compare the versions you read against the versions now current — but performed at object granularity, at explicit merge points chosen by the application, possibly long after the fact. TL2 overwrites locations and discards read sets at commit in the name of throughput; Manikin deliberately pays the storage cost of keeping both, trading TL2's performance envelope for auditability, event sourcing, and rebase.

Versioned Boxes as the Basis for Memory Transactions

Cachopo, Rito-Silva · Science of Computer Programming 63(2), pp. 172-185 (earlier version at SCOOL 2005) · 2006

JVSTM's versioned boxes are the STM design closest to Manikin's data model: each transactional location keeps a history of committed values, so read-only transactions run against a consistent timestamp-indexed snapshot and can never conflict or abort. Manikin generalizes the versioned box from a memory cell to a whole typed object (Id[O] mapping to id:version states) and gets the same free-reads property — reading any historical world version conflicts with nothing. The crucial divergence is intent: JVSTM's history is an internal performance mechanism, garbage-collected once no live transaction can need old versions and invisible to the programmer, whereas Manikin's history is a permanent, programmer-visible semantic feature that postconditions, the event log, model checking, and rebase all read from.

Open Nesting in Software Transactional Memory

Ni, Menon, Adl-Tabatabai, Hosking, Hudson, Moss, Saha, Shpeisman · PPoPP 2007 (12th ACM SIGPLAN Symposium on Principles and Practice of Parallel Programming), pp. 68-78 · 2007

Representative of the nested/open-transaction line: open-nested child transactions publish their effects before the parent commits, using abstract locks and programmer-written compensating actions to recover abstract serializability when word-level conflict detection is too strict for modular abstractions. Manikin's eff stage, which sends messages to other objects, produces nested dispatch trees whose read/write sets fold into the enclosing world step — closed nesting in effect — and it reaches open nesting's real goal (abstraction-level rather than memory-level conflicts) by tracking dependencies per object identity instead. Manikin needs no compensation machinery at all: since worlds are immutable and nothing is destructively published, abandoning a fork is simply dropping a value.

Transactional Boosting: A Methodology for Highly-Concurrent Transactional Objects

Herlihy, Koskinen · PPoPP 2008 (13th ACM SIGPLAN Symposium on Principles and Practice of Parallel Programming), pp. 207-216 · 2008

Boosting wraps linearizable objects so that conflicts are detected at method level via programmer-declared commutativity specifications, with rollback implemented by executing declared inverse operations. Manikin shares the central insight that the right conflict granularity is semantic operations on objects, not memory words — its merge effectively asks whether two message histories commute — and its rebase, which re-executes messages semantically from the common ancestor, echoes boosting's operation-level (rather than state-level) treatment of concurrency. But Manikin derives conflict detection automatically from the recorded read/write sets of each dispatch, requiring neither commutativity annotations nor inverses, because immutable worlds make rollback a non-operation; the price is coarser (possibly conservative) conflicts than a hand-written commutativity spec would allow.

CCSTM: A Library-Based STM for Scala

Bronson, Chafi, Olukotun · First Annual Scala Workshop, Scala Days 2010 (basis of the ScalaSTM library, industrial system) · 2010

CCSTM — which evolved into ScalaSTM, the de facto standard STM API for Scala — shows a pure library STM on the JVM: explicit Ref cells, transactional reads/writes as method calls, and a hybrid static/dynamic scoping trick to keep composability without compiler support. It is Manikin's nearest neighbor in embedding strategy: both are unprivileged JVM libraries using Scala's syntax flexibility (implicits, closures) to make transactional code read naturally. They diverge on what a transaction is for: CCSTM/ScalaSTM delimits atomic blocks over mutable Refs to coordinate concurrent threads in one address space, while Manikin's unit is the message over immutable worlds, so 'transactions' (forked worlds) can span arbitrary wall-clock time, be merged or rebased long after creation, and be re-targeted to different World implementations for event sourcing or distributed execution — capabilities outside ScalaSTM's design space, which like all STMs discards read/write metadata at commit.

A History of Clojure

Hickey · Proceedings of the ACM on Programming Languages, Vol. 4, HOPL (HOPL IV), Article 71 · 2020

Documents Clojure's ref/STM system and the epochal time model: identities are stable names for a causally ordered succession of immutable values, and mutation is confined to MVCC transactions over refs inside dosync. Manikin's Id[O] designating a series of immutable id:version states is Hickey's identity/value decomposition made typed and explicit, and both systems route all state change through a transactional mechanism over immutable data. The concurrency semantics differ sharply: Clojure's STM gives snapshot isolation and detects only write conflicts, so write skew must be prevented manually with ensure, whereas Manikin records every read (contracts included) and its merge rejects read/write intersections automatically, yielding serializability; and where Clojure's older values survive only as long as in-flight transactions reference them, Manikin's survive forever, giving it the event log, old-state postconditions, and git-style rebase that Clojure's model has no room for.

Added in the completeness pass

Nested Transactions: An Approach to Reliable Distributed Computing

Moss · MIT Press (monograph; MIT PhD thesis 1981) · 1985

The foundation of transaction nesting: child transactions commit into their parents, and only the top-level commit is durable — the model beneath both open nesting (already surveyed) and Argus. Manikin’s eff stage, whose message sends form a dispatch tree folded into one world step, is closed nesting in Moss’s exact sense; citing the source clarifies that Manikin’s nesting semantics are inherited, not invented.

6 Database isolation and optimistic concurrency control

where PostgreSQL's SSI approximates conflicts to cheaply admit more schedules and aborts on suspicion, Manikin computes conflicts exactly but conservatively, and recovers the lost schedules by semantically replaying the losing world's messages instead of discarding its work.

Manikin's merge sits squarely in the optimistic-concurrency-control lineage: merge(w1,w2) is Kung-Robinson backward validation performed over exact per-object read and write sets that the World records automatically on every dispatch, including reads made while evaluating pre- and postconditions. Because read/write intersections are checked and not just write/write, merge rejects write skew (Berenson et al.'s A5B) by construction, placing it on the serializable side of the Adya taxonomy rather than at snapshot isolation, and making it the application-level cousin of Yabandeh's write-snapshot isolation. The contrast with SSI must be stated carefully: Cahill/Röhm/Fekete and PostgreSQL detect a conservative dangerous structure over approximate, granularity-promoted conflict metadata (false positives from heuristics and from SIREAD lock promotion), but they admit schedules containing a single rw-antidependency; Manikin's fast path is exact at object granularity yet its criterion — complete read/write disjointness of the forked worlds — is stricter than serializability itself, rejecting overlaps that a simple one-before-the-other ordering would permit. So Manikin eliminates granularity-induced false positives while introducing criterion-induced ones, and it compensates not by refining the test (PSSI's exact cycle detection is the precision endpoint there) but with rebase: semantic replay of the recorded messages from the common ancestor, turning would-be aborts into re-executions — something no kernel-level scheduler can offer because it never sees the application's messages, only their reads and writes. What Manikin adds to this thread is that isolation stops being a hidden scheduler property and becomes a programming-model operation on immutable first-class worlds (fork/merge/rebase, git-like), portable unchanged across World implementations from in-memory testing to a serializable distributed engine such as CockroachDB. What it lacks relative to the thread: predicate/phantom handling (read sets are keyed by object identity), Herlihy-style commutativity-based validation, and any performance evaluation comparable to the engine papers.

The notions of consistency and predicate locks in a database system

Eswaran, Gray, Lorie, Traiger · Communications of the ACM 19(11), pp. 624-633 · 1976

Established serializability as the correctness criterion for concurrent transactions, framed correctness via application consistency predicates, and identified the phantom problem, proposing predicate locks over logical subsets of the database. Manikin adopts serializability as its merge criterion, and its pre/pst contract clauses are executable descendants of the paper's consistency predicates; because Worlds record the concrete reads performed while evaluating those predicates, predicate evaluation is covered by the tracked read set without symbolic predicate locks. The limitation to note: Manikin's read sets are keyed by object identity, so phantom-style anomalies over collections of identities are prevented only when the collection is itself a versioned worldly object whose read is recorded.

On Optimistic Methods for Concurrency Control

Kung, Robinson · ACM Transactions on Database Systems 6(2), pp. 213-226 · 1981

Introduced optimistic concurrency control with read/validation/write phases: serial validation commits a transaction iff its read set is disjoint from the write sets of concurrently committed transactions. Manikin's merge(w1,w2) is precisely this backward validation, but symmetric (both worlds' read and write sets are intersected against each other) and lifted to application level over typed object identities rather than storage records. Where Kung-Robinson restarts a failed transaction from scratch, Manikin's rebase replays the recorded messages from the common ancestor world, after which the paper guarantees the subsequent merge succeeds — recovery by semantic re-execution instead of blind retry.

Multiversion Concurrency Control - Theory and Algorithms

Bernstein, Goodman · ACM Transactions on Database Systems 8(4), pp. 465-483 · 1983

The foundational theory of multiversion concurrency control: each write produces a new version, and correctness is one-copy serializability over multiversion schedules. Manikin is multiversion by construction — every successful dispatch yields a new id:version pair and forked worlds therefore read from consistent snapshots for free, which is what makes pairwise merge validation well-defined. The difference is that MV theory treats versions as engine-internal artifacts to be garbage-collected, whereas Manikin retains every version forever as user-addressable state doubling as the event-sourced audit log.

Apologizing versus asking permission: optimistic concurrency control for abstract data types

Herlihy · ACM Transactions on Database Systems 15(1), pp. 96-124 · 1990

Moves optimistic validation from read/write classification up to typed abstract data types, exploiting operation semantics (commutativity) to accept interleavings that read/write conflict analysis would reject. Manikin shares the lifting of concurrency control to typed objects and operations (messages to Id[O]), but its merge deliberately stays with plain read/write set intersection and never reasons about message commutativity. It recovers flexibility operationally instead — rebase re-executes messages against the merged state, so two semantically compatible worlds can still be combined — but Herlihy-style type-specific conflict relations are an extension Manikin lacks, and a natural future-work citation.

A Critique of ANSI SQL Isolation Levels

Berenson, Bernstein, Gray, Melton, O'Neil, O'Neil · SIGMOD 1995, pp. 1-10 · 1995

Defined snapshot isolation precisely and named its signature anomaly, write skew (A5B): two transactions each read both items of a constraint and write disjoint items, preserving neither. This is the exact anomaly Manikin's merge rule targets — a merge that intersected only write sets would reproduce SI and admit A5B, so checking read/write intersections is what pushes merge past snapshot isolation. Manikin additionally makes the violated constraint explicit: a pst postcondition spanning multiple objects (e.g. 'sum of both account balances unchanged') is checked at dispatch, so write skew would be caught even by assertion where the merge-set argument is the structural guarantee.

Weak Consistency: A Generalized Theory and Optimistic Implementations for Distributed Transactions

Adya · PhD thesis, MIT (Technical Report MIT/LCS/TR-786) · 1999

Gives implementation-independent specifications of isolation levels via direct serialization graphs and phenomena G0-G2, deliberately compatible with optimistic and multiversion implementations, plus optimistic validation schemes for client-side transactions in the Thor object store. Adya supplies the vocabulary in which Manikin's guarantee should be stated: worlds combined by a successful fast-path merge are mutually conflict-free, so the merged history is trivially free of G1/G2 phenomena between them. Manikin also revives Adya's architectural setting — optimistic transactions executed against client-local object state and validated later — but turns validation from a server-side commit-time check into a user-callable merge on immutable first-class world values.

Making Snapshot Isolation Serializable

Fekete, Liarokapis, O'Neil, O'Neil, Shasha · ACM Transactions on Database Systems 30(2), pp. 492-528 · 2005

Proved that every non-serializable execution under SI contains a dangerous structure of two consecutive rw-antidependencies around a pivot transaction, and proposed static analysis of an application's transaction programs (static dependency graph, plus materialize/promote rewrites) to guarantee serializable execution on an SI engine. Manikin reaches the same end without whole-application static analysis: Worlds capture exact read/write sets dynamically at every message dispatch, and the serializability-relevant check runs per merge. The trade is runtime bookkeeping on every dispatch — acceptable in an embedded DSL, and exactly the cost Fekete et al.'s offline approach was designed to avoid in a database engine.

Serializable Isolation for Snapshot Databases

Cahill, Röhm, Fekete · SIGMOD 2008, pp. 729-738 (extended version in ACM TODS 34(4), 2009) · 2008

Serializable Snapshot Isolation: detect Fekete et al.'s dangerous structure at runtime using SIREAD locks and abort a transaction with both an inbound and outbound rw-antidependency — conservative, since two consecutive rw edges need not close a cycle, so false positives occur. Both SSI and Manikin detect rw conflicts dynamically, but they err in different directions: SSI admits schedules containing a single antidependency, while Manikin's fast-path merge fails on any rw overlap between forked worlds — a criterion stricter than serializability. Manikin's compensations are exactness (per-object sets, no lock-table approximation) and rebase, which converts a failed merge into semantic replay rather than a lost transaction; a fair comparison must concede that SSI's schedule admissibility on the fast path is strictly larger.

Precisely Serializable Snapshot Isolation (PSSI)

Revilak, O'Neil, O'Neil · ICDE 2011, pp. 482-493 · 2011

Eliminates SSI's false positives by maintaining the full dependency graph and aborting only when an actual cycle forms — zero spurious aborts relative to serializability, at the cost of retaining graph history for overlapping transactions. PSSI is the precision endpoint of this thread and calibrates Manikin's claim: Manikin's read/write sets are exact, but its acceptance criterion (complete disjointness of forked worlds) is coarser than PSSI's cycle test, so Manikin must not claim maximal precision. What Manikin offers instead is that its exact conflict information is exposed as an application-level, composable operation on first-class worlds, with rebase recovering the schedules its conservative criterion rejects.

Serializable Snapshot Isolation in PostgreSQL

Ports, Grittner · PVLDB 5(12), pp. 1850-1861 (VLDB 2012) · 2012

The first production SSI implementation; candidly documents its false-positive sources — dangerous structures that never close into cycles, and SIREAD lock granularity promotion (tuple to page to relation) under bounded memory — plus mitigations like safe snapshots and commit-ordering refinements. This is the paper against which Manikin's 'exact per-object intersections' contrast must be stated fairly: PostgreSQL's imprecision is largely an engineering choice to bound conflict-tracking memory in a server, whereas Manikin can afford full read/write sets and complete version history only because worlds are application-scale values. Correctly framed, Manikin eliminates granularity-induced false positives but introduces criterion-induced ones (rw overlaps that a serial order would permit), masking them via rebase rather than via a more refined test.

A critique of snapshot isolation

Yabandeh, Gómez Ferro · EuroSys 2012, pp. 155-168 · 2012

Introduces write-snapshot isolation: keep SI's snapshot reads but replace write-write validation with centralized read-write validation — abort a committing transaction whose read set intersects the write sets of concurrent committed transactions — which yields full serializability at SI-like cost (built for a lock-free centralized certifier in the HBase/Omid lineage). Among engine-side algorithms this is the nearest neighbor to Manikin's merge condition, since both certify by intersecting read sets with concurrent write sets, and both argue the rw check is the one that matters for correctness. Manikin differs in checking write/write intersections as well — necessary because merge must produce a single consistent object graph, not merely certify an order — and in replacing the centralized certifier with pairwise merge of immutable worlds plus rebase as the fallback.

CockroachDB: The Resilient Geo-Distributed SQL Database

Taft, Sharif, Matei, VanBenschoten, Lewis, Grieger, Niemi, Woods, Birzin, Poss, Bardea, Ranade, Darnell, Gruneir, Jaffray, Zhang, Mattis · SIGMOD 2020, pp. 1493-1509 (industrial system) · 2020

Industrial serializable-by-default distributed SQL engine using MVCC with timestamp ordering; when a transaction's commit timestamp is pushed, its 'read refresh' mechanism re-validates that the transaction's read spans are unchanged at the newer timestamp before committing — an engine-level cousin of Manikin's merge-time read-set revalidation. CockroachDB matters to Manikin twice: it is the named backend for Manikin's distributed World implementation, illustrating the layering claim that business logic keeps identical fork/merge/rebase semantics while durability and cross-node isolation are delegated to a serializable engine; and it shows the same rw-revalidation idea deployed at datacenter scale. Manikin adds the application-visible programming model above such engines; it inherits rather than reproduces their availability and performance engineering.

Added in the completeness pass

Sagas

Garcia-Molina, Salem · SIGMOD 1987, pp. 249–259 · 1987

The canonical answer to long-lived transactions: break them into a sequence of sub-transactions, each with a compensating action to run if the whole fails — accepting non-serializability in exchange for availability. Manikin is the counter-proposal for the same problem shape: a long-lived unit of work is a forked world, which needs no compensation logic because nothing is published until merge; rebase replaces compensation. Event-sourcing practice pushes cross-aggregate invariants into sagas; Manikin keeps them in one atomic dispatch tree with a postcondition.

Sinfonia: A New Paradigm for Building Scalable Distributed Systems

Aguilera, Merchant, Shah, Veitch, Karamanolis · SOSP 2007 (ACM TOCS 27(3), 2009) · 2007

Coined the minitransaction: a short atomic unit bundling compare items, read items, and write items, piggybacked onto the commit protocol. Since Manikin describes its own messages as four-stage mini-transactions, the comparison is obligatory: a Sinfonia minitransaction’s compare-then-write over memory ranges is structurally a Manikin pre-then-app over typed objects — but Sinfonia’s compare sets are declared statically up front for protocol efficiency, while Manikin’s read sets are discovered by executing arbitrary condition code, which is what lets contracts participate in conflict detection.

Feral Concurrency Control: An Empirical Investigation of Modern Application Integrity

Bailis, Fekete, Franklin, Ghodsi, Hellerstein, Stoica · SIGMOD 2015 · 2015

Empirically shows that application-level invariants in Rails applications — validations and associations checked feral-ly in application code without database coordination — are frequently unsafe under concurrency, quantifying how often. It is the motivational bridge between two of this survey’s threads: Manikin’s pre/pst contracts are exactly such application-level invariants, but coupled to recorded read sets and serializable merge so that the anomalies Bailis et al. measure (including the write-skew shape) are detected rather than silently admitted.

7 Concurrent revisions and deterministic parallelism

Concurrent Revisions makes every join succeed by predeclaring per-type merge functions and gives up serializability; Manikin lets merges fail on precise read/write-set intersections and repairs them by semantic rebase, giving up determinism to keep serializability and cross-object contracts.

A related-work section should place Manikin squarely inside the fork-join-state family that Concurrent Revisions crystallized: computation forks logical copies of shared state, reconciles them at an explicit join, and the version-control analogy is taken seriously as a programming model rather than a metaphor — Manikin's fork/merge/rebase over immutable Worlds is a revision diagram in Burckhardt et al.'s sense. The decisive axis for separating Manikin from every system in this thread is conflict-freedom versus conflict-detection. Revisions and their descendants (the Rev monad, cloud types, and OS-level systems like Grace and Dthreads) guarantee that every join succeeds — via per-type merge functions, lattice joins, or last-writer-wins diffs — buying unconditional determinism at the explicit cost of serializability; DPJ and LVars go further and make conflicts statically or structurally impossible. Manikin makes the inverse trade: it records exact per-dispatch read and write sets (crucially including reads performed inside pre- and postconditions), lets merge fail precisely when write/write or read/write intersections are non-empty — which detects write skew and yields serializable-snapshot-grade semantics with exact per-object sets rather than PostgreSQL-style approximate dangerous-structure detection — and recovers via semantic rebase replay from the common ancestor, after which merge is guaranteed. What Manikin adds beyond the thread is the coupling of this discipline to design-by-contract (multi-object postconditions ride the same read-set machinery) and to swap-in World implementations for event sourcing, model checking, and execution on serializable databases. What it lacks, and should concede openly, is this thread's headline property: merge outcomes depend on fork/merge order and timing, so Manikin is neither deterministic (revisions, DPJ, LVars, Dthreads) nor statically conflict-free (DPJ, LVars), and it has no formal semantics comparable to the ESOP 2011 revision calculus.

Semantics of Concurrent Revisions

Burckhardt, Leijen · ESOP 2011 (LNCS 6602) · 2011

Gives the revision calculus: a formal fork/join semantics for concurrent revisions with a proof of determinacy (confluence), and shows precisely how the model relates to — and departs from — serializability and snapshot isolation. It is the formal benchmark for Manikin's design point: Burckhardt and Leijen prove their joins commute because merge functions resolve all conflicts, which entails abandoning serializability, while Manikin's merge precondition (empty write/write and read/write intersections between forked worlds) is exactly the condition under which snapshot-style merging is serializable, i.e. it detects write skew that snapshot isolation admits. Manikin currently has only an executable semantics; a paper would need a comparable calculus for merge/rebase, and this is the model to formalize against.

Prettier Concurrency: Purely Functional Concurrent Revisions

Leijen, Fähndrich, Burckhardt · Haskell Symposium 2011 · 2011

Embeds concurrent revisions in Haskell as a Rev monad, showing the model has a pure denotational reading — imperative-looking revision computations can be safely converted back into pure values, with no rollback and deterministic conflict resolution (contrasted by the authors with STM). This is the closest methodological cousin to Manikin's embedding of Worlds as immutable first-class values in Java/Scala/Kotlin, and the sharpest stylistic foil: where Leijen et al. thread state through a monad, Manikin explicitly rejects monadic plumbing and hides a mutable Environment behind a ThreadLocal (the author's 'inverse of a monad') so business logic reads imperatively while worlds remain pure values. Manikin should cite it both as precedent for library-level revision embeddings and as the design it consciously deviates from.

Two for the Price of One: A Model for Parallel and Incremental Computation

Burckhardt, Leijen, Sadowski, Yi, Ball · OOPSLA 2011 · 2011

Extends concurrent revisions with record/repeat: execution builds a dynamic dependence graph so that on repeat only subcomputations whose dependencies changed are re-executed, yielding parallel self-adjusting computation from the same fork/join abstractions. It is the revisions-line precedent for Manikin's central implementation idea that a world should record fine-grained dependencies of execution: Manikin likewise logs every dispatch with its full read/write sets, but spends that information on merge admissibility checking and semantic rebase replay rather than on incremental recomputation. The paper shows a capability Manikin's recorded event log could support but does not currently exploit (incremental re-execution), while Manikin's per-object contract checks have no counterpart here.

Cloud Types for Eventual Consistency

Burckhardt, Fähndrich, Leijen, Wood · ECOOP 2012 (LNCS 7313) · 2012

Transplants revision diagrams to the distributed setting: client devices fork and join revisions of cloud data declared via cloud types (CInt, CString, entities), with fork-join automata giving eventual consistency and automatic, type-directed conflict resolution. Like Manikin's swap-in World implementations, it shows one revision-based programming model spanning local and distributed execution without changing application code. The contrast is the consistency target: cloud types guarantee convergence because every join succeeds via built-in resolution (no serializability), whereas Manikin distributes by running worlds on an already-serializable store (e.g. CockroachDB) and refuses merges it cannot serialize, preserving cross-object invariants at the cost of coordination and possible merge failure.

LVars: Lattice-based Data Structures for Deterministic Parallelism

Kuper, Newton · FHPC 2013 (workshop at ICFP) · 2013

Achieves determinism-by-construction through shared variables whose states form a user-specified lattice, permitting only monotonic (least-upper-bound) writes and 'threshold' reads that block until a lower bound is passed — so all schedules commute and conflicts cannot exist. This is the opposite pole from Manikin within deterministic/isolated concurrency: LVars restrict what programs may express so no conflict detection is ever needed, while Manikin allows arbitrary object state transitions guarded by pre/postconditions and detects conflicts post hoc from recorded read/write sets. Manikin gains generality (non-monotonic business logic like debiting an account) and serializability, but provides no determinism guarantee of any kind, which LVars provide unconditionally.

Freeze After Writing: Quasi-Deterministic Parallel Programming with LVars

Kuper, Turon, Krishnaswami, Newton · POPL 2014 · 2014

Extends LVars (the LVish library) with freezing and event handlers, weakening the guarantee to quasi-determinism: every run either produces the same answer or raises a write-after-freeze exception. It is a useful intermediate point for positioning Manikin because it, too, admits a runtime failure outcome as the price of expressiveness — a write-after-freeze error is structurally analogous to a failed Manikin merge. The difference is recovery and target property: LVish has no repair path and still aims at (quasi-)determinism, while Manikin's rebase semantically replays messages from the common ancestor so an initially failing merge can still commit, and the property defended is serializability plus contract invariants, not determinism.

A Type and Effect System for Deterministic Parallel Java

Bocchino, Adve, Dig, Adve, Heumann, Komuravelli, Overbey, Simmons, Sung, Vakilian · OOPSLA 2009 · 2009

Deterministic Parallel Java guarantees deterministic semantics for a Java subset by a static region-based type and effect system: programmers annotate heap regions and method effects, and the compiler proves parallel tasks noninterfering (disjoint read/write effects) before the program runs. DPJ and Manikin reason about the same object — read/write effect sets over shared objects — but at opposite binding times: DPJ computes conservative effect disjointness statically and rejects programs at compile time, while Manikin records exact read/write sets dynamically per message dispatch (including reads inside pre/postconditions) and rejects merges at run time, with rebase as recovery. Manikin needs no annotations or effect polymorphism and admits data-dependent access patterns DPJ cannot type, but it forgoes DPJ's static guarantee that conflicts never occur.

The Implementation of the Cilk-5 Multithreaded Language

Frigo, Leiserson, Randall · PLDI 1998 · 1998

The landmark fork/join work-stealing runtime whose 'determinism' is conditional: a Cilk program is deterministic only if it is free of determinacy races, a property of the particular program (checkable by tools such as the Nondeterminator) rather than of the model, since spawned tasks share the heap directly. The briefing's Cilk-vs-revisions contrast triangulates Manikin: Cilk offers unconditional sharing with conditional determinism, Concurrent Revisions offers isolation with unconditional determinism, and Manikin offers isolation (forked immutable worlds) with unconditional serializability but no determinism — conflicting histories surface as explicit merge failures rather than silent races. Manikin borrows only the fork/join control skeleton from this line; its contribution is entirely in the state semantics Cilk leaves unmanaged.

Grace: Safe Multithreaded Programming for C/C++

Berger, Yang, Liu, Novark · OOPSLA 2009 · 2009

Runs fork/join C/C++ threads as OS processes with copy-on-write page-level isolation, tracks per-page read and write sets via virtual memory protection, and commits threads in sequential order, rolling back and re-executing any thread whose read/write set conflicts with an earlier commit — yielding sequential semantics for unmodified code. Mechanically this is the nearest ancestor of Manikin's detect-and-redo discipline: both compute read/write sets and re-execute on conflict rather than merging values. Manikin differs in granularity and semantics: its sets are logical (per object-version, per message, including reads made by contracts), avoiding false page-level conflicts, and its rebase replays messages semantically against the new base — so a rebase can succeed and even change results legitimately where Grace's byte-level re-execution model would simply retry — while Grace needs no source changes at all, which Manikin, as an embedded DSL, plainly requires.

Dthreads: Efficient Deterministic Multithreading

Liu, Curtsinger, Berger · SOSP 2011 · 2011

A drop-in pthreads replacement that makes arbitrary C/C++ programs deterministic: threads run as processes on private copies of memory and their byte-level diffs are committed in a fixed deterministic order at synchronization points, with overlapping writes resolved last-writer-wins. It represents the OS-level endpoint of concurrency-by-merge: like Concurrent Revisions it guarantees every merge succeeds, but by syntactic memory diffing with an imposed commit order, silently resolving races and thus not preserving the program's intended serial semantics. Manikin sits at the opposite extreme — merges are semantic, may fail, and are checked against application-level read/write sets and multi-object postconditions — trading Dthreads' universality and determinism for meaning-preserving, serializable application state.

8 Speculative execution and optimistic replay added in the completeness pass

Time Warp rolls one timeline back to repair a global order; Manikin never rolls back at all — it forks immutable timelines and repairs by replaying the loser onto the winner.

Manikin’s most distinctive mechanism — rebase, the semantic replay of messages from a common ancestor after a failed merge — has its deepest precedent in a thread none of the survey’s original fourteen covered: optimistic execution with rollback and re-execution. Jefferson’s Virtual Time is the canon: processes race ahead on local virtual clocks, and a straggler message rolls the process back to a saved state and replays it, with anti-messages cancelling what should not have been sent. Manikin inherits the optimistic-execute-then-repair shape but changes every coordinate: rollback is free (a fork is simply dropped — immutable worlds need no anti-messages or state-saving protocol), the trigger is a failed sibling merge rather than a straggler in one global virtual order, and validation consults exact recorded read/write sets rather than timestamps. Galois supplies the PL-side lesson that conflicts must be detected semantically, at the abstraction level — which Manikin endorses while replacing Galois’s programmer-declared commutativity conditions and inverse methods with automatically recorded dependency sets and no inverses at all. Safe Futures show the same read/write-tracking discipline preserving serial semantics on the JVM, but inside one linear program. A reviewer who knows Jefferson 1985 would have named this thread’s absence first; it belongs in the core related-work section.

Virtual Time

Jefferson · ACM TOPLAS 7(3), pp. 404–425 · 1985

The canonical optimistic synchronization paper: Time Warp processes execute speculatively against local virtual clocks, save state periodically, and on receiving a straggler message roll back and re-execute, sending anti-messages to cancel invalidated output. Manikin’s rebase is the same repair-by-replay move with the mechanics inverted by immutability: no state-saving protocol (every version is already retained), no anti-messages (nothing was published — an abandoned fork is dropped), and no single virtual order (validation is a symmetric read/write-set intersection between sibling worlds rather than timestamp comparison). Time Warp targets throughput in distributed simulation; Manikin targets serializable reconciliation of application state.

Distributed Simulation and the Time Warp Operating System

Jefferson, Beckman, Wieland, Blume, DiLoreto, Hontalas, Laroche, Sturdevant, Tupman, Warren, Wedel, Younger, Bellenot · SOSP 1987 · 1987

The systems realization of Virtual Time on the JPL Mark III hypercube, demonstrating that wholesale optimistic rollback/replay is buildable and profitable at OS scale, with fossil collection reclaiming state no rollback can reach. Fossil collection is the mirror image of Manikin’s retention policy: Time Warp keeps history only until global virtual time passes it, while Manikin keeps history forever because postconditions, event sourcing, and rebase all read from it — the same information, opposite lifetime.

Optimistic Parallelism Requires Abstractions

Kulkarni, Pingali, Walter, Ramanarayanan, Bala, Chew · PLDI 2007 · 2007

The Galois system speculatively parallelizes irregular algorithms and detects conflicts semantically: shared objects declare commutativity conditions between their methods, and speculative work is undone via programmer-supplied inverse methods. It is the strongest PL statement of Manikin’s own premise that memory-level conflict detection is the wrong level of abstraction. The difference is automation and recovery: Galois needs commutativity specifications and inverses (like transactional boosting), whereas Manikin derives conflicts from recorded per-object read/write sets and needs no inverses because immutable worlds make undo a non-operation.

Safe Futures for Java

Welc, Jagannathan, Hosking · OOPSLA 2005 · 2005

Makes Java futures transparently safe by tracking read/write dependencies between a future and its continuation and revoking/re-executing the continuation when serial semantics would be violated — object-granularity dependency tracking with replay-based repair on the JVM, the same ingredients as Manikin’s merge/rebase. But safe futures preserve the semantics of one sequential program, so validation is against a fixed serial order; Manikin validates symmetric sibling worlds with no a-priori order, and surfaces conflicts to the programmer as failed merges rather than transparent revocations.

9 Actors, virtual actors, and transactors

where actors and transactors bolt consistency onto asynchronous messages, Manikin bolts messages onto a consistent versioned world — dispatch is a synchronous transaction, and asynchrony survives only as the forking and merging of immutable histories.

Manikin inherits the actor lineage's core discipline — stateful entities addressed by identity that interact only by sending messages (Hewitt 1973; Agha 1986) — and Orleans' virtual-actor move of making identity primary with materialization on demand: Id[O] with its init factory is a semantic twin of grain activation, transposed from a distributed runtime into a pure world value. But it departs from the entire thread on the axis the thread treats as definitional: asynchrony. Every family in De Koster et al.'s taxonomy (classic actors, active objects, processes, communicating event loops) makes delivery asynchronous and interleaving the source of both concurrency and nondeterminism, whereas a Manikin dispatch is synchronous and world-threaded — a deterministic, replayable four-stage mini-transaction with pre/postconditions — and nondeterminism reappears only at the fork/merge of immutable worlds under exact read/write-set conflict detection. Its closest relatives are therefore the transactional fringes of the thread: Field & Varela's transactors, which add dependence tracking and decentralized globally-consistent checkpointing to actors for fault tolerance, and Orleans Transactions (Eldeeb et al., MSR-TR-2016 through PVLDB 2024), which impose lock-based distributed ACID commits on asynchronous grain calls. Manikin is the inverse construction: rather than retrofitting transactional guarantees onto asynchronous messaging, it starts from transactions — worlds as versioned snapshots, merge as SSI-grade certification that additionally catches write skew via precise read-set/write-set intersections — and recovers message passing inside them. Relative to this thread Manikin adds design-by-contract postconditions that span the multiple objects a message cascade touched (no actor system checks a cross-actor invariant like "sum of both balances unchanged") and a git-like, semantically mergeable history; it lacks everything the thread was invented for — location transparency, distribution, supervision and partial-failure handling, and intra-world parallelism — recovering distribution only by swapping in a World backed by a serializable database.

A Universal Modular ACTOR Formalism for Artificial Intelligence

Hewitt, Bishop, Steiger · IJCAI 1973 (Proc. 3rd International Joint Conference on Artificial Intelligence, pp. 235-245) · 1973

The origin of the actor model: computation as autonomous actors that hold private state and interact solely by sending messages. Manikin keeps exactly this discipline — all interaction is dispatching a Message to a typed identity, never touching another object's state — but inverts the concurrency stance: actor sends are asynchronous with nondeterministic arrival order, while a Manikin dispatch is a synchronous, deterministic four-stage transaction (pre/app/eff/pst) threaded through an immutable World. Manikin adds per-dispatch read/write-set recording and full versioned history, which the actor formalism has no notion of; it gives up the model's inherent parallelism inside a single world.

Actors: A Model of Concurrent Computation in Distributed Systems

Agha · MIT Press (monograph) · 1986

Systematized the actor model with an operational semantics: an actor processes one message per turn, changes state via 'become', and may only send messages and create actors; fairness and arbitrary interleaving are built in. Manikin's app stage (pure old-state to new-state function) is a functional analogue of become, and its eff stage — restricted to sending messages to other objects plus a return value — mirrors the permitted outputs of an actor turn. The decisive difference is that Agha makes interleaving the essence of concurrency, whereas Manikin serializes all dispatches within a world and moves concurrency to world fork/merge with conflict certification; Manikin's multi-object postconditions have no counterpart in classical actor theory (the nearest relative, Field and Varela's transactors, tracks cross-actor consistency but offers no contract-style assertions spanning objects).

Making reliable distributed systems in the presence of software errors

Armstrong · PhD thesis, KTH Royal Institute of Technology, Stockholm · 2003

The design rationale of Erlang/OTP: isolated lightweight processes with immutable data, asynchronous message passing, and reliability through 'let it crash' plus supervision trees rather than defensive checks. Manikin shares the immutable-values, message-only-interaction discipline but sources reliability oppositely: design-by-contract pre/postconditions verified on every dispatch, with a failed contract aborting the whole world transition atomically instead of crashing and restarting a process. Erlang offers battle-tested distribution and fault tolerance that Manikin lacks; Manikin offers deterministic replay and read/write-set-certified merges that Erlang's runtime-nondeterministic mailboxes cannot express (Mnesia's transactions are a bolt-on library, not part of the message semantics).

On the integration of the actor model in mainstream technologies: the Scala perspective

Haller · AGERE!@SPLASH 2012 workshop, ACM (pp. 1-6); documents Scala Actors and Akka (industrial system) · 2012

The citable account of how the actor model was industrialized on the JVM, from Scala Actors to Akka: asynchronous fire-and-forget tell on (then-untyped) ActorRefs, supervision hierarchies, with event-sourced state later added as the opt-in Akka Persistence module. Manikin occupies the same ecological niche — a Scala/JVM embedded model for stateful applications — but chooses opposite defaults: typed identities Id[O], synchronous dispatch returning a value, and event sourcing as an intrinsic property of every World rather than a persistence add-on. Akka delivers parallelism and distribution out of the box; Manikin delivers determinism, replayability, and cross-object contract checking out of the box.

Orleans: Cloud Computing for Everyone

Bykov, Geller, Kliot, Larus, Pandya, Thelin · ACM Symposium on Cloud Computing (SoCC 2011) · 2011

Introduces grains — isolated actor-like units of state and computation addressed by identity, communicating through asynchronous messages with promises — and, notably, the original design provided 'lightweight transactions that support a consistent view of state' by exploiting isolated state and a constrained execution model to persist, replicate, and reconcile grain state (verified in the abstract; this transaction mechanism was dropped before the open-source 1.0 release and revisited a decade later). Identity-based addressing with runtime-managed materialization directly parallels Manikin's Id[O].init producing pristine state on first reference. The contrast: Orleans reconciles asynchronously-produced grain states in a distributed runtime, while Manikin makes the consistent view primitive — one immutable world — and delegates distribution to a swap-in World implementation over a serializable store.

Orleans: Distributed Virtual Actors for Programmability and Scalability

Bernstein, Bykov, Geller, Kliot, Thelin · Microsoft Research tech report MSR-TR-2014-41 · 2014

Names the 'virtual actor' abstraction: a grain exists logically forever; physical activations are created on demand when a message arrives and reclaimed transparently, so programmers never manage lifecycle, placement, or failure of individual actors. This is the closest published analogue of Manikin's identity discipline — Id[O].init makes every identity denote a valid pristine object before any message arrives, turning worlds into total functions from identity to state — i.e., a purely semantic counterpart of on-demand activation. Orleans virtualizes actors to solve distributed resource management; Manikin virtualizes objects to enable versioned history (id:version) and deterministic replay, and has none of Orleans' runtime machinery (placement, load balancing, fault tolerance).

Transactions for Distributed Actors in the Cloud

Eldeeb, Bernstein · Microsoft Research tech report MSR-TR-2016-1001 · 2016

First design of ACID multi-actor transactions for the virtual-actor setting, attacking the core problem that locks held across two-phase commit's forced writes to slow cloud storage kill throughput; proposes an early-lock-release commit protocol among transaction managers. Shares Manikin's central concern — making a message cascade spanning several actors atomic and serializable — but is pessimistic, lock-based, and distributed. Manikin obtains atomicity for free because the entire cascade executes inside one immutable world; isolation is certified optimistically at merge time by exact read/write-set intersection, with no locks, coordinators, or forced writes in the model.

Cloud Actor-Oriented Database Transactions in Orleans

Eldeeb, Burckhardt, Bond, Cidon, Yang, Bernstein · PVLDB 17(12), pp. 3720-3730 (VLDB 2024) · 2024

The archival account of Orleans Transactions as shipped (the briefing's 'VLDB 2024?' is correct — this resolves the 2016 tech report's uncertain fate): distributed ACID transactions over pluggable cloud storage, using reconnaissance queries to prefetch actor state before lock acquisition and early lock release so locks are almost never held across storage latency. It is the industrial state of the art for transactional messaging among virtual actors and the natural head-to-head for Manikin's merge: both provide serializability across multi-object message flows, but Orleans certifies at commit against storage via locking, while Manikin certifies at merge against a sibling world via read/write intersections, detecting write skew with SSI-grade precision at application level. Manikin additionally checks semantic postconditions across the touched objects — Orleans has no analogue — but lacks Orleans' fault-tolerance and throughput engineering.

Transactors: a programming model for maintaining globally consistent distributed state in unreliable environments

Field, Varela · POPL 2005, ACM (pp. 195-208) · 2005

Verified against the paper itself: transactors extend actors with dependence tracking on volatile state received in messages and with stabilize/checkpoint/rollback semantics, formalized as the tau-calculus (an actor-based extended lambda calculus) with an operational semantics and two theorems — safety (traces reaching globally-consistent checkpoints are equivalent to failure-free traces) and liveness (checkpoints are reachable given a bounded failure-free interval) — composing transaction-processing elements without central coordination. It is Manikin's closest theoretical relative in this thread: both track the fine-grained dependencies that message flow creates among object states and define multi-object consistency semantically. The targets differ: transactors pursue fault tolerance under node failure, Manikin pursues isolation between concurrent world forks — dependence tracking becomes read/write sets, checkpoints become immutable world versions, rollback becomes discarding a fork. Manikin adds contracts and deterministic replay but does not model node failure at all.

Robust Composition: Towards a Unified Approach to Access Control and Concurrency Control

Miller · PhD thesis, Johns Hopkins University · 2006

Defines E's concurrency architecture: objects live in vats (communicating event loops) with immediate synchronous calls inside a vat and eventual asynchronous sends with promises between vats — no shared state, no blocking, and deterministic turn-by-turn execution within each vat (the model is also detailed in Miller, Tribble & Shapiro, 'Concurrency Among Strangers', TGC 2005, LNCS 3705). Manikin shares the conviction that plan interference must be prevented by the programming model and the turn discipline of running each message to completion deterministically. But E's cross-vat consistency remains a plan-coordination problem solved by protocol (promises, escrow), whereas Manikin makes the entire multi-object cascade one synchronous transaction in one world, so cross-object atomicity is primitive; Manikin says nothing about E's other pillar, object-capability security.

AmbientTalk: Object-oriented Event-driven Programming in Mobile Ad hoc Networks

Van Cutsem, Mostinckx, Gonzalez Boix, Dedecker, De Meuter · XXVI International Conference of the Chilean Computer Science Society (SCCC 2007), IEEE (pp. 3-12) · 2007

Carries the E-style communicating-event-loop model to mobile ad hoc networks: strictly non-blocking futures, messages buffered across disconnections, and network partition treated as a normal mode of operation rather than a failure. It marks the asynchronous-by-necessity extreme of the actor design space and clarifies by contrast what Manikin's synchronous world-threading buys — deterministic replay and cross-object contracts — and what it forgoes: AmbientTalk has a first-class story for partial failure and disconnection, Manikin has none (its distribution story is delegated wholesale to a serializable database backend).

43 years of actors: a taxonomy of actor models and their key properties

De Koster, Van Cutsem, De Meuter · AGERE 2016 workshop (6th International Workshop on Programming Based on Actors, Agents, and Decentralized Control), ACM (pp. 31-40) · 2016

Classifies actor systems into four families — classic actors, active objects, processes, and communicating event loops — along axes of interface, delivery guarantees, and state isolation; all four share asynchronous message delivery as the source of concurrency. The taxonomy gives a related-work section the vocabulary to place Manikin precisely: within a world, Manikin fits none of the four families, since dispatch is synchronous with transactional bracketing and recorded read/write effects; across worlds it behaves like an optimistic versioning/STM system rather than an actor runtime. Citing it supports the claim that 'worldly objects' are a distinct point in the design space — actor-style identity and message-only interaction with the asynchrony removed.

Life beyond Distributed Transactions: an Apostate’s Opinion

Helland · CIDR 2007, pp. 132–141 · 2007

The influential argument that at scale one must give up cross-entity transactions: entities are identity-keyed, hold their own state, and coordinate through messages with at-least-once delivery and application-level compensation. Manikin’s distributed story is a direct rejoinder from the opposite premise — keep multi-object atomicity by delegating durability to a serializable store and doing cross-entity coordination as world merges — making Helland 2007 the sharpest statement of the position Manikin’s design bets against (and Helland 2015, already surveyed, the manifesto it agrees with).

10 Language-integrated transactions and orthogonal persistence added in the completeness pass

Argus bought atomicity with locks, logs, and stable storage; Manikin gets it by construction — a world transition either produces a new immutable world or it never happened.

Before STM, there was a lineage that made transactions a construct of the programming language itself, over identity-bearing objects — and Manikin visibly recombines its ingredients. Argus made atomic actions (with nesting) linguistic primitives over guardians and atomic objects; Thor executed client-side operations optimistically against cached typed objects and validated at the server (the setting from which Adya’s isolation theory grew); the orthogonal-persistence programme held that persistence should be orthogonal to type and code, so the same program text runs against transient or durable state. Manikin restates each claim in versioned form: every message dispatch is an atomic action whose atomicity comes from world immutability rather than locking and stable storage; optimistic client execution becomes forked worlds validated at user-invoked merge rather than server commit; and swap-in Worlds are orthogonal persistence at world granularity — identical business logic runs in-memory, event-sourced, or on a serializable database, except that what persists is the full version history, not merely the current object graph. What the lineage has that Manikin lacks is equally clear: a real failure model, distribution as a first-class concern, and decades of engineering for cache coherence and recovery.

Guardians and Actions: Linguistic Support for Robust, Distributed Programs

Liskov, Scheifler · ACM TOPLAS 5(3), pp. 381–404 · 1983

Argus is the founding language-integrated-transactions work: guardians encapsulate state behind handlers, and atomic actions — serializable, recoverable, and nestable — are the linguistic unit of computation over atomic objects. Manikin keeps the shape (typed stateful entities, transaction-per-interaction, nesting via the eff stage’s dispatch tree) and swaps every mechanism: two-phase locking and stable storage become world immutability and version retention; recovery becomes dropping a fork; and Argus’s pessimistic isolation becomes optimistic merge-time validation. Argus addresses node failure and distribution head-on, which Manikin delegates wholesale to a backing store.

Safe and Efficient Sharing of Persistent Objects in Thor

Liskov, Adya, Castro, Day, Ghemawat, Gruber, Maheshwari, Myers, Shrira · SIGMOD 1996 · 1996

Thor is a distributed object database in which clients run transactions optimistically against locally cached typed objects and the server validates at commit — the architecture from which Adya’s generalized isolation specifications (already in the database-isolation thread) emerged. Manikin revives Thor’s client-side optimism but reifies it: the “cache” is an immutable first-class world, and validation is not a hidden server step but a user-callable merge whose read/write-set criterion the application can observe, retry, or rebase around. Thor’s cache-coherence and garbage-collection engineering has no Manikin counterpart.

Orthogonally Persistent Object Systems

Atkinson, Morrison · VLDB Journal 4(3), pp. 319–401 · 1995

The definitive statement of orthogonal persistence: an object’s longevity should be independent of its type and of the code that manipulates it, eliminating the mapping layer between program objects and stored data. Manikin’s swap-in Worlds satisfy the principle at a coarser grain — business logic is oblivious to whether its world is transient, event-sourced, or database-backed — but what persists is characteristically different: not the reachable object graph but the entire versioned history plus the read/write-annotated event log, i.e., persistence of computation structure, not just state. The PS-algol/Napier88 systems surveyed persist one mutable heap with no versioning or merge.

III.Branching, merging, and history

11 Git-like branch-and-merge data management

where every existing branch-and-merge store asks whether two divergent *states* can be reconciled, Manikin asks whether the *computations* that produced them ever read what the other wrote.

Manikin sits squarely in the "git for data" lineage — fork immutable state, work on branches, merge later — but it occupies a corner of that design space that is nearly empty: the merge criterion. Every store in this thread decides mergeability by inspecting *states or values*: Irmin, Noms/Dolt and ForkBase run 3-way structural or user-supplied value merges over content-addressed snapshots; TARDiS exposes conflicting branches and delegates the merge function to the application; Decibel, OrpheusDB and DataHub version relational snapshots at record granularity; MRDTs and Banyan derive always-converging value merges from relational abstractions of data types. Manikin instead decides mergeability by intersecting the *semantic read and write sets recorded during message execution* — including reads performed inside pre- and postconditions — so merge(w1,w2) succeeds iff write/write and read/write intersections are empty, which detects write skew and yields serializable-snapshot-isolation-grade guarantees that no value-based merge can offer (a 3-way merge happily accepts two branches that each read state the other overwrote). Its rebase operation likewise replays *messages* (intentions) from the common ancestor rather than transplanting diffs, which is the semantic analogue of the patch-commutation machinery formalized syntactically by Darcs/Pijul patch theory (Mimram & Di Giusto; Homotopical Patch Theory). What Manikin lacks relative to this thread is everything below the language surface: no persistent content-addressed storage engine or delta encoding (ForkBase, Decibel, Dolt's Prolly trees), no replication or geo-distribution story (TARDiS, Irmin, Banyan), and no guarantee of convergence — Manikin merges can fail and demand a rebase, where MRDT-style systems always converge coordination-free.

TARDiS: A Branch-and-Merge Approach To Weak Consistency

Crooks, Pu, Estrada, Gupta, Alvisi, Clement · SIGMOD 2016 (pp. 1615-1628) · 2016

TARDiS is a transactional key-value store for weakly consistent geo-replication that, instead of hiding divergence, branches state on conflict, records all branches in a state DAG with fork/merge points, and lets applications atomically merge branches by supplying explicit merge logic over consistent branch snapshots. It is the closest database-systems ancestor of Manikin's fork/merge worlds: both make branches a first-class abstraction that applications reason about. But TARDiS forks reactively on write-write conflict and delegates reconciliation to application-written merge functions over values, whereas Manikin forks proactively (worlds are always immutable), decides merge admissibility automatically from recorded read/write-set intersections (catching write skew, which TARDiS's per-key conflict detection does not track), and falls back to semantic replay via rebase. Manikin lacks TARDiS's replication, durability, and multi-consistency-level machinery — it is an in-process programming model, not a distributed store.

Irminsule; a branch-consistent distributed library database

Gazagnaire, Chaudhry, Crowcroft, Madhavapeddy, Mortier, Scott, Sheets, Tsipenyuk · OCaml Users and Developers Workshop 2014 · 2014

Irmin (introduced as Irminsule) is an OCaml library database that transplants Git's object model — content-addressed immutable blocks, branches, and 3-way merges with a common ancestor — onto typed application data, letting programs fork and merge their state like repositories; it later became the storage layer of MirageOS and Tezos. Manikin shares the core move of making application state a persistent, branchable value with git-like operations embedded in a typed functional language. The decisive difference is the merge oracle: Irmin merges by invoking per-type, user-supplied 3-way merge functions on values, with no record of what a computation read, while Manikin needs no per-type merge code because conflicts are defined by intersection of automatically recorded read/write sets, so it rejects write-skew interleavings that a value-level 3-way merge silently accepts. Irmin in turn offers durable storage, Git-format interoperability, and distributed synchronization that Manikin does not attempt.

Mergeable persistent data structures

Farinier, Gazagnaire, Madhavapeddy · JFLA 2015 (Journées Francophones des Langages Applicatifs) · 2015

This companion paper to Irmin shows how to extend purely functional data structures (queues, ropes) with 3-way merge operations and analyzes their complexity, arguing that ordinary persistent data structures plus a merge function suffice to build branch-consistent stores. It shares Manikin's foundation — immutable, versioned functional state as the substrate for concurrency — but represents exactly the per-data-type, value-merge philosophy Manikin rejects: each new structure requires hand-crafted merge semantics, and merges consider only the two states plus ancestor, not the operations or reads that produced them. Manikin replaces this with one uniform, type-agnostic criterion (empty read/write intersection) plus rebase-by-replay of messages, at the cost of sometimes refusing merges that a domain-specific merge function could reconcile.

Noms ("The versioned, forkable, syncable database") and Dolt ("Git for Data")

Boodman, Weinstein et al. (Attic Labs); Sehn et al. (DoltHub) · industrial systems (Attic Labs 2016; DoltHub 2019-) · 2016

Noms (Attic Labs, 2016) invented Prolly trees — probabilistic, content-addressed B-trees whose diff and merge cost scales with the size of the change — to build a decentralized database with full Git semantics over structured data; Dolt (DoltHub, from 2019) carried the design into a MySQL-compatible SQL database where branch, commit, diff, and merge are SQL-level operations, and is the most prominent industrial realization of the briefing's 'git for data' theme. Both share Manikin's explicit Git analogy and retention of every historical version, and their structural diffs are far more storage-efficient than Manikin's in-memory version maps. But their merges are cell-wise/row-wise reconciliations of snapshots: two transactions that each read rows the other wrote merge without complaint, precisely the anomaly Manikin's read/write-set intersection is designed to reject. Manikin conversely has no persistence layer or delta-encoded storage — it addresses merge semantics, not merge storage.

ForkBase: An Efficient Storage Engine for Blockchain and Forkable Applications

Wang, Dinh, Lin, Xie, Zhang, Cai, Chen, Ooi, Ruan · PVLDB 11(10):1137-1150 (VLDB 2018) · 2018

ForkBase is a storage engine providing git-like multi-version branching (both on-demand and on-conflict forking) with a pattern-aware, content-addressed POS-tree that deduplicates across versions and supplies tamper evidence for blockchain workloads. It demonstrates that fork/merge semantics can be pushed into the storage layer for efficiency — the layer Manikin deliberately abstracts away behind swap-in World implementations. The contrast is again the merge criterion: ForkBase tracks version lineage of values and resolves conflicts structurally or by application policy, with no notion of a transaction's read footprint, whereas Manikin's worlds record full read and write sets per message dispatch and define conflict as their intersection. A ForkBase-style engine would be a natural persistent backend for Manikin worlds; Manikin adds the transactional semantics ForkBase leaves to the application.

DataHub: Collaborative Data Science & Dataset Version Management at Scale

Bhardwaj, Bhattacherjee, Chavan, Deshpande, Elmore, Madden, Parameswaran · CIDR 2015 · 2015

DataHub is the vision paper that imported git's branch/merge model into the database community: a hosted platform with a dataset version control system supporting create, branch, merge, diff, and search over large divergent dataset collections, explicitly motivated by git's unsuitability for large structured data. It frames the same question Manikin answers at the programming-language level — what does version control mean for structured, live data rather than text files — and spawned the Decibel/OrpheusDB implementation line. DataHub versions and merges datasets at record granularity with no semantics attached to how versions were produced; Manikin versions objects produced by message transactions and merges on the recorded semantic dependencies of those transactions, but offers none of DataHub's multi-user hosting, query, or scale ambitions.

Decibel: The Relational Dataset Branching System

Maddox, Goehring, Elmore, Madden, Parameswaran, Deshpande · PVLDB 9(9):624-635 (VLDB 2016) · 2016

Decibel, DataHub's storage substrate, is the first serious systems study of how to physically store branched relational data, comparing tuple-first, version-first, and hybrid layouts with bitmap-encoded version membership, and contributing a branching benchmark. It shares Manikin's commitment to keeping every version of every object addressable (Manikin's id:version pairs are a naive main-memory analogue of Decibel's versioned tuples). But Decibel's branches carry no transactional semantics — merging is set reconciliation of tuple versions, and the system neither records what analyses read nor defines conflict beyond divergent tuples — while Manikin's whole contribution is that merge admissibility is derived from read/write dependencies of executed messages. Decibel conversely addresses storage efficiency at data scales Manikin's in-memory maps cannot approach.

OrpheusDB: Bolt-on Versioning for Relational Databases

Huang, Xu, Liu, Elmore, Parameswaran · PVLDB 10(10):1130-1141 (VLDB 2017) · 2017

OrpheusDB bolts dataset versioning onto an unmodified PostgreSQL by representing collaborative versioned datasets as relations with rid-array version membership, plus the LyreSplit partitioning algorithm to bound version-checkout latency — gaining full SQL analytics 'for free' on versioned data. Its bolt-on strategy is the database mirror of Manikin's swap-in World strategy: both retrofit versioning onto an existing substrate (Postgres vs. plain JVM objects) without changing the host's core. The difference is what a version means: OrpheusDB versions are passive record sets whose merge is membership union with conflicts surfaced to users, while Manikin versions are outputs of pre/post-condition-checked transactions whose merge is refused when recorded read/write sets intersect. Manikin lacks OrpheusDB's query capabilities and any comparable storage-sharing analysis.

A Categorical Theory of Patches

Mimram, Di Giusto · ENTCS 298 (MFPS XXIX), pp. 283-307 · 2013

Mimram and Di Giusto model repositories categorically — files as objects, patches as morphisms — and define merging as the pushout (with residuals from pushout cocones), obtaining by universal property the merge semantics that Darcs pursued informally; this theory underlies Pijul (the briefing's 'Pijul categories of patches' refers to this line, not a separate Pijul paper). The connection to Manikin is rebase: computing how one line of work transports over another is exactly patch residuation. But the theory is syntactic — patches are edits to file contents, and two patches commute iff their textual effects are independent — whereas Manikin's units are semantic messages with recorded read/write footprints, transported by literal re-execution (rebase replays messages and re-checks pre/postconditions) rather than by a residual calculus. Manikin thus trades the theory's compositional guarantees for semantic fidelity; it has no formal metatheory of comparable rigor, a genuine gap a paper should admit.

Homotopical Patch Theory

Angiuli, Morehouse, Licata, Harper · ICFP 2014 (expanded in JFP 26, 2016) · 2014

This paper reconstructs Darcs-style patch theory inside homotopy type theory: a patch theory is a higher inductive type whose points are repository contexts and whose paths are patches, so patch laws (composition, inversion, commutation) hold by construction, and interpretations into concrete repositories arise functorially via univalence. It is the deepest formal treatment of the branch/merge substrate Manikin builds on, and its separation of an abstract patch theory from its interpretation parallels Manikin's separation of message semantics from swap-in World implementations. The divergence mirrors the Mimram/Di Giusto entry: HPT's patches are proof-relevant syntactic edits with mandatory invertibility, whereas Manikin's messages are generally non-invertible state transitions whose conflict structure comes from dynamically recorded read/write sets — nothing in HPT tracks what a patch read. Manikin offers no mechanized semantics; HPT offers no executable system.

Mergeable Replicated Data Types

Kaki, Priya, Sivaramakrishnan, Jagannathan · PACMPL 3(OOPSLA), Article 154 (OOPSLA 2019) · 2019

MRDTs derive a correct 3-way merge for any inductive data type automatically from an invertible relational abstraction of its state (merge the relations set-theoretically, concretize back), and execute atop Quark, a Git-like content-addressed branching store — replacing hand-written CRDT convergence logic with derived value merges. This is the strongest PL-side statement of the value-merge philosophy: like Manikin it embeds git-style branch/merge in a typed language over immutable state, but its merges always succeed and guarantee convergence, achieving availability by construction while permitting interleavings (e.g., write skew across relationally independent components) that violate serializability. Manikin makes the opposite trade: merges consult read/write dependency sets and can fail, forcing a rebase, in exchange for SSI-grade application-level isolation and multi-object postconditions that MRDTs cannot express. The briefing's tentative 'Concordant/AntidoteDB?' entries were deliberately dropped from this thread: AntidoteDB (the Cure protocol) merges CRDT values under causal consistency and belongs to the CRDT/eventual-consistency thread, not the branch-merge-store thread.

Banyan: Coordination-Free Distributed Transactions over Mergeable Types

Dubey, Sivaramakrishnan, Gazagnaire, Madhavapeddy · APLAS 2020 (LNCS 12470, Springer) · 2020

Banyan layers a distributed transaction abstraction over Irmin/MRDT-style mergeable types on a Git-like store (implemented over Scylla): each client works on its own branch, a transaction is a fork-work-merge episode, and coordination-freedom is achieved because MRDT merges never fail. It is the published system closest to Manikin's 'transaction = branch of an immutable world' model, arrived at independently in the same time frame. The difference is exactly Manikin's thesis: Banyan buys always-available commits by accepting whatever the type-level value merge produces, providing no isolation-level guarantee against read-write anomalies, whereas Manikin's merge inspects recorded read/write sets, rejects write skew, and guarantees the equivalent of serializable snapshot isolation, with rebase-by-replay as the recovery path. Banyan handles distribution and durability; Manikin handles neither natively but adds design-by-contract postconditions spanning multiple objects, which Banyan's merges cannot check.

12 Optimistic replication: Bayou, OT, and CRDTs

where Bayou asks the programmer to hand-write a dependency-check query approximating each write's conflicts and settles for a single-master eventual order, Manikin records the exact read set of every precondition, transition, and postcondition as it runs, turning Bayou's per-write conflict heuristic into an automatic, write-skew-detecting, serializable merge criterion.

This thread — optimistic replication and convergence — shares Manikin's founding bet: execute updates immediately against a local copy and reconcile divergence after the fact. It splits into two families. The syntactic-convergence family (OT from Ellis & Gibbs through Jupiter; CRDTs from Shapiro et al. through Automerge and Peritext) guarantees that concurrent replicas always merge, but only by restricting operations to transformable or commutative forms, and it is structurally blind to application invariants — the canonical failure being cross-object constraints like a non-negative sum over two accounts, exactly the write-skew shape Manikin's merge detects. The semantic-reconciliation family (Bayou, IceCube, TARDiS, Indigo) consults application logic instead, and Bayou is Manikin's nearest ancestor: Bayou's dependency check anticipates Manikin's read-set validation, its merge procedure anticipates rebase, and its tentative-versus-committed writes anticipate forked-versus-merged worlds. Manikin's advance over this family is threefold: read/write sets are recorded automatically and per-object by executing the typed pre/app/eff/pst stages, rather than hand-written as Bayou's approximate queries or Indigo's statically analyzed invariant/operation pairs; the merge criterion is application-level serializability (empty write/write and read/write intersections, so postcondition reads participate in conflict detection) rather than Bayou's eventual primary-decided total order or TARDiS's programmer-written state-merge functions; and contracts, conflict detection, and replay fall out of one language-level construct — the four-stage Message — instead of separate per-system machinery. What Manikin lacks relative to this thread is equally clear: no coordination-free availability (a merge can fail where a CRDT merge cannot), no anti-entropy or epidemic propagation protocol, and no per-datatype intent preservation for concurrent edits to the same object.

Managing Update Conflicts in Bayou, a Weakly Connected Replicated Storage System

Terry, Theimer, Petersen, Demers, Spreitzer, Hauser · SOSP 1995 · 1995

Bayou attaches to every write an application-supplied dependency check (a query plus expected result) and a merge procedure; writes are tentative until a primary commits them into a canonical total order, and replicas roll back and replay tentative writes when that order changes — structurally the closest published ancestor of Manikin's rebase, which likewise replays messages semantically onto a new ancestor. The differences are precise: Bayou's dependency checks are hand-written per-write queries that only approximate the true read footprint, whereas Manikin's Worlds record the exact read set of pre/app/eff/pst as they execute; Bayou converges to a single-master eventual order with no isolation guarantee, whereas Manikin's merge requires empty write/write and read/write intersections, i.e. serializability with write-skew detection. Bayou also has no typed contracts — a merge procedure may write anything — while Manikin surfaces a failed pre- or postcondition during rebase as a first-class outcome rather than resolving it silently.

Session Guarantees for Weakly Consistent Replicated Data

Terry, Demers, Petersen, Spreitzer, Theimer, Welch · PDIS 1994 (3rd Int. Conf. on Parallel and Distributed Information Systems) · 1994

The Bayou group's companion paper defines the four per-session guarantees (read-your-writes, monotonic reads, writes-follow-reads, monotonic writes) that make read-any/write-any replication tolerable to a single client, specified via per-session read- and write-sets and implemented practically with version vectors. It names exactly the consistency properties that optimistic systems weaken and that Manikin gets for free: a Manikin world is an immutable snapshot, so all reads within it are trivially monotonic and read-your-writes, and cross-world consistency is settled wholesale at merge time rather than piecemeal per session. The contrast is useful for positioning: session guarantees patch weak consistency from the client side, while Manikin's fork/merge model never exposes an inconsistent intermediate state to business logic at all.

The IceCube Approach to the Reconciliation of Divergent Replicas

Kermarrec, Rowstron, Shapiro, Druschel · PODC 2001 · 2001

IceCube treats reconciliation as log-based scheduling: divergent replicas' action logs are reordered subject to application-declared static constraints between action pairs and dynamic constraints (preconditions) checked by simulated execution, searching for a schedule that maximizes accepted actions. It shares with Manikin's rebase the core move — replay logged operations semantically against a merged state and let preconditions veto them — but the mechanics invert: IceCube requires the programmer to declare inter-action constraints explicitly and performs combinatorial search over orders, while Manikin fixes the order (winner's history, then loser's messages replayed) and derives all conflicts automatically from recorded read/write sets and contract evaluation. Manikin thus trades IceCube's schedule optimization for zero per-application reconciliation code; it lacks IceCube's ability to salvage a better ordering when the default one fails.

Putting Consistency Back into Eventual Consistency

Balegas, Duarte, Ferreira, Rodrigues, Preguiça, Najafzadeh, Shapiro · EuroSys 2015 · 2015

Indigo proposes explicit consistency: application invariants are declared in first-order logic, a static analysis identifies which operation pairs can jointly violate them when run concurrently, and violations are prevented at runtime via reservation/escrow protocols layered on a causally consistent store. It shares Manikin's central claim that application invariants — not structural convergence — are the right criterion for admissible concurrency, and its invariants play the same role as Manikin's pst postconditions. The mechanism differs completely: Indigo analyzes invariants statically and avoids conflicts proactively with distributed reservations, while Manikin evaluates postconditions dynamically at dispatch and rebase time and, crucially, records their read footprint so that an invariant's reads participate in merge conflict detection — which is exactly how Manikin catches write skew that pairwise-commuting updates would slip past. Indigo scales to geo-replication where Manikin has only single-store distributed backends; Manikin needs no offline analysis step.

Concurrency Control in Groupware Systems

Ellis, Gibbs · SIGMOD 1989 · 1989

The paper that introduced operational transformation (the dOPT algorithm): concurrent operations execute immediately at each site and arriving remote operations are transformed against locally executed ones so all sites converge without locking. It shares Manikin's optimistic-execution premise, but reconciles by syntactically rewriting operations via hand-written transformation functions for every operation pair — a per-datatype effort notorious for subtle correctness bugs (dOPT itself was later shown incorrect) — whereas Manikin never rewrites a message: rebase re-executes messages unchanged against the merged state and lets their contracts accept or veto them. OT guarantees convergence for the one data structure it was engineered for; Manikin guarantees serializability and invariant preservation for arbitrary object graphs, at the cost that a merge can fail outright.

High-Latency, Low-Bandwidth Windowing in the Jupiter Collaboration System

Nichols, Curtis, Dixon, Lamping · UIST 1995 · 1995

Jupiter made OT practical by routing all operations through a central server that pairwise-transforms against each client, reducing the n-site transformation problem to n client-server pairs; this architecture is the direct ancestor of Google Wave and Google Docs. Its centrally-arbitrated canonical order parallels Manikin's rebase onto a designated winning world (and Bayou's primary commit order), but Jupiter's correctness target is convergence plus intention preservation for shared-widget state, with no notion of application invariants or isolation. Manikin generalizes the 'one authoritative order, others replay' pattern from windowing state to arbitrary contract-carrying business objects; it does not attempt Jupiter's real-time, per-keystroke latency envelope.

Conflict-Free Replicated Data Types

Shapiro, Preguiça, Baquero, Zawirski · SSS 2011 (13th Int. Symp. on Stabilization, Safety, and Security of Distributed Systems); extended version INRIA RR-7687 · 2011

Formalizes strong eventual consistency and the two CRDT constructions (state-based join-semilattices and commutative operation-based types) whose replicas provably converge without coordination or rollback. CRDTs solve the same divergence problem as Manikin's world merge but from the opposite end: they restrict object semantics until every merge succeeds by construction, which makes them unable to maintain non-local invariants — a constraint spanning two counters (Manikin's flagship 'transfer preserves total balance' postcondition) is exactly what CRDTs cannot express. Manikin keeps arbitrary state transitions and multi-object invariants, paying for it with merges that can fail and a rebase slow path; CRDTs keep availability and guaranteed convergence, paying with a severely restricted design space.

A Conflict-Free Replicated JSON Datatype

Kleppmann, Beresford · IEEE Transactions on Parallel and Distributed Systems 28(10) · 2017

Defines a CRDT for arbitrarily nested JSON maps and lists with a formal small-step semantics and convergence proof; it is the theoretical basis of Automerge, the most widely deployed general-purpose CRDT library (industrial lineage the briefing names). Like Manikin it is a generic substrate — application programmers get merge behavior without writing conflict-resolution code — but its resolution policies are fixed and structural (concurrent map/list edits merged positionally, concurrent register assignments kept as multi-value conflicts or resolved last-writer-wins), so a merge can silently produce states no sequential execution would reach. Manikin's merge admits only serializable outcomes and checks postconditions across objects; conversely Automerge merges always terminate successfully offline, which Manikin's fail-and-rebase model cannot promise.

Peritext: A CRDT for Collaborative Rich Text Editing

Litt, Lim, Kleppmann, van Hardenberg · Proc. ACM Hum.-Comput. Interact. 6(CSCW2), article 531 · 2022

Peritext (from Ink & Switch, the Automerge ecosystem) is the first published CRDT for rich text with inline formatting, engineering stable span anchors and per-mark merge rules so that concurrent offline edits preserve authors' formatting intent. It marks the endpoint of the CRDT trajectory relevant to Manikin: each new data type with nontrivial semantics demands a bespoke, research-grade merge design encoding 'intent' into the type itself. Manikin externalizes intent instead — messages carry executable pre/postconditions and rebase replays them — so no per-datatype merge design exists at all, but Manikin correspondingly offers nothing like Peritext's fine-grained intra-document merging: two worlds editing the same object simply conflict.

Optimistic Replication

Saito, Shapiro · ACM Computing Surveys 37(1) · 2005

The field's canonical survey, whose taxonomy (state transfer vs. operation transfer; syntactic vs. semantic scheduling and conflict detection; single-master vs. multi-master commitment) gives the vocabulary a related-work section needs. In its terms Manikin is a multi-master, operation-transfer system with semantic conflict detection — but the survey documents that semantic detection in prior systems (Bayou, IceCube, Ficus) always meant programmer-supplied predicates or resolvers, whereas Manikin mechanizes it: read/write dependencies are captured by executing the operations' own contracts. The survey also states the field's guiding rule that optimistic systems trade consistency for availability; Manikin occupies an unusual cell by keeping optimistic multi-master execution while insisting on serializable merges.

Local-First Software: You Own Your Data, in spite of the Cloud

Kleppmann, Wiggins, van Hardenberg, McGranaghan · Onward! Essays 2019 (SPLASH) · 2019

This essay articulates the programme Manikin's concurrency story serves: application state that supports offline work, branching, and merging 'like git', with CRDTs proposed as the foundation technology and explicit lament that version-control-grade workflows do not exist for application data. Manikin, contemporaneous and independent, is a direct answer to that lament — fork/merge/rebase over typed application objects with the git analogy made executable — but it rejects the essay's CRDT premise: instead of guaranteed convergence with fixed structural merges, it offers contract-checked serializable merges that can fail. Manikin does not, however, deliver the essay's distribution ideals (peer-to-peer sync, end-to-end encryption, indefinite offline operation); its distributed mode leans on a serializable database rather than coordination-free replicas.

Time, Clocks, and the Ordering of Events in a Distributed System

Lamport · CACM 21(7), pp. 558–565 · 1978

Defines happens-before, logical clocks, and the state-machine replication idea that a totally ordered log of deterministic commands determines state — the theoretical bedrock under every event log and replay mechanism in this survey, Manikin’s included. Manikin’s divergent worlds are concurrent in exactly Lamport’s partial-order sense; where classical SMR fabricates a total order first and applies commands second, Manikin executes first and certifies afterwards that no order is needed (merge) or constructs one (rebase).

13 Blockchain state machines and parallel execution added in the completeness pass

Block-STM records read/write sets, validates by intersection, and re-executes the invalidated — Manikin’s pipeline exactly, except the chain already knows the total order, and Manikin’s whole point is that there isn’t one yet.

The largest deployed system matching Manikin’s shape is one the original survey never named: the account-based blockchain. Ethereum’s Yellow Paper describes identity-addressed accounts, each with distinct state, interacting “through a message-passing framework,” advanced by deterministic transactions replayed from an append-only log — and a chain reorganization is precisely a system-scale rebase: discard a suffix of history, re-execute transactions on the winning branch. The parallel-execution literature then converges on Manikin’s exact machinery from the throughput side: Dickerson et al. have miners execute contract transactions speculatively under STM and publish a fork-join schedule that validators replay deterministically, and Block-STM validates optimistically executed transactions by their recorded read/write sets, re-executing invalidated ones — record, validate by intersection, replay: Manikin’s merge/rebase pipeline, deployed at planetary scale. The differences are structural: consensus fixes one total order (Block-STM validates against a preset serialization within a block; there is no sibling-world merge, and reorg-rebase is winner-takes-all with no read/write reconciliation), smart-contract “contracts” are code with revert semantics rather than declarative pre/postconditions, and the adversarial setting imposes gas metering and determinism constraints Manikin never faces. A reviewer will ask why the largest industrial instance of message-as-mini-transaction over identity-addressed immutable state goes unmentioned; the answer must be this section.

Ethereum: A Secure Decentralised Generalised Transaction Ledger (Yellow Paper)

Wood · self-published formal specification (industrial) · 2014

The first formal blockchain specification: a replicated state-transition machine over identity-addressed accounts whose state changes only by deterministic transactions, totally ordered by consensus and replayable from the log; reorganizations discard and re-execute a suffix of history on the heavier branch. Structurally this is Manikin’s model — identities, message mini-transactions, event-log replay, rebase — hardened for an adversarial, decentralized setting. What it lacks relative to Manikin is exactly Manikin’s thesis: there is no sibling merge (consensus picks one branch and the other’s effects vanish), no read/write-set reconciliation, and no declarative contracts (EVM code reverts instead of asserting).

Adding Concurrency to Smart Contracts

Dickerson, Gazzillo, Herlihy, Koskinen · PODC 2017 (journal version Distributed Computing 33, 2020) · 2017

Miners speculatively execute a block’s smart-contract transactions in parallel using abstract-lock/STM techniques, then publish the discovered serializable fork-join schedule so validators can replay it deterministically in parallel. The paper imports exactly the semantic-conflict machinery of the STM/boosting line (Herlihy and Koskinen are authors of both) into the replicated-state setting, and its record-then-deterministically-replay split mirrors Manikin’s event log enabling rebase. It optimizes execution of an already-agreed transaction sequence; Manikin uses the same information to decide whether independently forked histories can lawfully combine.

Block-STM: Scaling Blockchain Execution by Turning Ordering Curse to a Performance Blessing

Gelashvili, Spiegelman, Xiang, Danezis, Li, Malkhi, Xia, Zhou · PPoPP 2023 · 2023

The production parallel-execution engine (Aptos; Diem lineage): transactions in a block run optimistically in parallel, each recording its read set (as version-stamped reads from a multi-version data structure) and write set; validation checks that recorded reads are still current, and invalidated transactions re-execute — all against the block’s preset serialization order. This is the closest industrial mechanism to Manikin’s merge/rebase: identical bookkeeping, identical repair-by-re-execution. The divergence is teleological: Block-STM enforces a total order it was handed, whereas Manikin’s merge certifies that no order is needed (disjoint read/write sets) and its rebase constructs one when it is; and Block-STM has no contracts, no history retention beyond the block, and no user-visible branching.

A Concurrent Perspective on Smart Contracts

Sergey, Hobor · WTSC @ Financial Cryptography 2017 (LNCS 10323) · 2017

Argues the analogy that smart contracts are concurrent objects: accounts are shared state, transactions are concurrent operations, and classic concurrency anomalies (including the DAO bug read as a reentrancy/atomicity violation) reappear on-chain. The paper legitimizes analyzing blockchain state with concurrency-control vocabulary — precisely the frame under which Manikin and the chain are instances of one design space — while offering analysis rather than mechanism; Manikin supplies the mechanism (contracts as checked pre/postconditions, conflicts as set intersections) that the analogy calls for.

14 Event sourcing and temporal data

event-sourcing systems remember what happened, but Manikin's worlds also remember what every event looked at — and that read provenance is precisely what turns an append-only history from a replayable record into a mergeable, serializable one.

A related-work section should place Manikin squarely inside the immutability/log-as-truth lineage — Helland's manifesto, Fowler and Young's event-sourcing canon, Kreps's log, LMAX, Akka Persistence, Datomic — while sharpening two axes on which it departs. First, log content: every surveyed system records only what was written (events, facts, assertions); none records what each command read — audit-oriented ES writing explicitly concedes that read operations are absent from event-sourced histories, and read-dependence tracking otherwise lives in adjacent literatures (database why-provenance à la Cheney/Chiticariu/Tan, and read-set tracking inside SSI implementations), not in the ES canon. Manikin's log captures the complete read/write trace of every dispatch, including reads made by pre- and postconditions and by recursive effects, and this is exactly the information that makes serializable merging of divergent logs decidable at application level. Second, timeline cardinality: event stores, temporal/bitemporal databases (TSQL2, SQL:2011), and Datomic all maintain one linear system-versioned timeline — Datomic's with() and Retro-λ's branches allow speculative or what-if divergence but never merge back with conflict detection — whereas Manikin makes forking first-class and closes the loop with read/write-set merge and semantic rebase, a coarse-grained realization of Demaine-style retroactivity. Honesty demands noting what Manikin lacks relative to this thread: no valid-time/bitemporal dimension, full-replay rebase rather than sublinear retroactive update, and no story for the log schema evolution that Overeem et al. show dominates ES maintenance.

Immutability Changes Everything

Helland · CIDR 2015 (republished ACM Queue 13(9) / CACM 2016) · 2015

Position paper arguing that append-only immutable data should pervade systems design — 'accountants don't use erasers': corrections are new entries, and cheap storage makes keeping every version affordable. Manikin operationalizes exactly this stance at the programming-model level: worlds, objects, and messages are all immutable values, every historical id:version is retained, and each successful dispatch appends to a log. Helland surveys where immutability shows up (LSM trees, DataSets, messaging) but offers no mechanism for reconciling divergent immutable histories; Manikin adds precisely that — merge/rebase of forked worlds certified by recorded read/write sets.

Event Sourcing

Fowler · martinfowler.com, Further Enterprise Application Architecture development (eaaDev) · 2005

The canonical pattern description: capture all changes to application state as a sequence of events, enabling rebuild of state, temporal query, and retroactive change handling by replay. Manikin makes this a built-in property of every World rather than an architectural decision — successful dispatches are appended automatically. The key delta is log content: Fowler's log records only the events, so his discussion of retroactive events must reason informally about which past computations a correction invalidates; Manikin's log additionally records each dispatch's full read and write sets (including reads inside pre/pst conditions and recursive effects), giving replay/rebase a mechanical dependency test.

CQRS Documents

Young · self-published, cqrs.wordpress.com (industrial) · 2010

Young's 56-page document codified the industrial ES+CQRS canon: commands validated against an aggregate rebuilt from its per-aggregate event stream, the stream as the transactional and optimistic-concurrency boundary (expected-version checks), and event storage design. Manikin's pre stage plays the command-validation role, but the validation's reads are themselves recorded in the read set — Young's validation reads leave no trace. More fundamentally, classical ES/CQRS confines a transaction to one aggregate and pushes cross-aggregate invariants into eventually-consistent sagas, whereas a single Manikin dispatch tree atomically spans multiple objects and its pst postcondition can assert a multi-object invariant (e.g. transfer preserves the sum of two balances) — we found no ES literature with such DbC-style multi-object postconditions.

The Log: What every software engineer should know about real-time data's unifying abstraction

Kreps · LinkedIn Engineering blog (industrial) · 2013

Frames the append-only, totally-ordered log as the unifying abstraction behind replication, state-machine replication, and data integration: the log is authoritative, tables are cached views. Manikin shares the log-as-truth stance — a World's event log is the durable record from which any state can be re-derived. But Kreps's log entries are opaque records whose consistency comes from imposing a single total order up front; Manikin's entries are typed messages annotated with precise read/write footprints, so two divergent logs (forked worlds) can be merged post hoc by dependency analysis instead of requiring one sequencer.

Turning the database inside-out with Apache Samza

Kleppmann · Confluent blog / Strange Loop 2014 talk (industrial) · 2015

Argues for making the replication log the primary database and deriving all materialized views (KV stores, search indexes, analytics) via stream processors — subsuming event sourcing as one instance of log-then-derive. Manikin's swap-in World implementations are the same inversion inside a programming language: the identical message history yields event sourcing, mock injection, model checking, or distributed execution depending on the World chosen. Kleppmann's derived views are eventually consistent and reads never enter the recorded history; Manikin records reads in each transaction's footprint and offers serializable merge of concurrent histories rather than eventual consistency.

The LMAX Architecture

Fowler · martinfowler.com, describing the LMAX trading platform (industrial system) · 2011

Documents LMAX's event-sourced, fully in-memory Business Logic Processor: every input event is journaled and deterministically replayable (for recovery, testing, and diagnostics), processing 6M orders/sec on a single thread fed by Disruptor ring buffers. Shares with Manikin the commitment to a deterministic in-memory domain model reconstructible from its event log. The contrast is concurrency strategy: LMAX buys consistency by forcing one total order through one thread, whereas Manikin lets independent computations proceed in forked worlds and restores serializability afterwards via read/write-set merge or semantic rebase; LMAX also has no contracts and no queryable version history.

Akka Persistence

Typesafe/Lightbend (Krasser, Nordwall, et al.) · industrial system, Akka 2.3 (JVM/Scala) · 2014

The closest industrial JVM analogue to Manikin's dispatch model: a persistent actor validates a command, persists the resulting immutable events to a pluggable journal, applies them to in-memory state, and recovers by replay (with snapshots). Like Manikin, entities are addressed by identity and mutated only through messages, and the journal backend is swappable without touching business logic — paralleling Manikin's swap-in Worlds. But each journal is a per-actor stream with no cross-actor transactions: causality between actors must be hand-encoded, command validation reads are unrecorded, and there are no postconditions; a single Manikin dispatch atomically covers the whole tree of effects across many objects and logs the complete read/write trace.

The Datomic Information Model (Datomic)

Hickey · InfoQ article describing Datomic (industrial system, Cognitect, launched 2012) · 2013

Datomic treats the database as an accumulation of immutable facts under an epochal time model: the database is a succession of immutable values, with db.asOf/db.since/db.history for transaction-time travel and db.with(tx) for speculative local futures. This is the database-side twin of Manikin's Worlds — both hand the program an immutable value of the entire state plus its full history. But Datomic has a single-writer transactor producing one linear timeline, its with() branches can never be merged back, and its log records only assertions/retractions — not what a transaction function read; Manikin makes branching first-class, records reads (including inside contracts), and can merge or rebase timelines with precise write/write and read/write conflict detection. Datomic's transaction functions are the closest analogue to Manikin messages but carry no pre/post contracts.

The TSQL2 Temporal Query Language

Snodgrass (ed.), with Ahn, Ariav, Batory, Clifford, Dyreson, Elmasri, Grandi, Jensen, et al. · Kluwer Academic Publishers (book; language committee specification) · 1995

The consensus temporal-SQL specification consolidating two decades of temporal-database research, establishing the valid-time vs transaction-time distinction and bitemporal tables (surveyed compactly in Jensen & Snodgrass, 'Temporal Data Management', IEEE TKDE 11(1), 1999); its lineage leads to SQL:2011 system-versioned tables. Manikin's retained id:version histories are transaction-time (system-versioned) data at object granularity, so 'state as of world w' queries come for free. Manikin lacks the valid-time dimension entirely — it cannot express bitemporal questions like 'what did we believe last Tuesday about the balance on Jan 1' — while temporal databases conversely version a single linear timeline with no notion of forked branches, merge, or per-transaction read provenance.

Retroactive Data Structures

Demaine, Iacono, Langerman · ACM Transactions on Algorithms 3(2), article 13 (preliminary version SODA 2004) · 2007

Formalizes data structures where operations can be inserted into or deleted from the past of the operation sequence, with changes propagating to the present — including the Ω(r) rollback lower bound and the partial/full retroactivity distinction, plus efficient retroactive queues, priority queues, and union-find. This is the algorithmic theory of what event-sourced replay does naively, and Manikin's rebase is exactly a coarse-grained retroactive operation: messages are semantically re-executed from the common ancestor, at full-replay cost rather than the sublinear bounds achieved here. Manikin's recorded read sets are the information one would need to skip re-executing dispatches whose reads are untouched — a bridge between ES practice and this theory that neither side currently exploits.

The Dark Side of Event Sourcing: Managing Data Conversion

Overeem, Spoor, Jansen · SANER 2017 (24th IEEE Intl. Conf. on Software Analysis, Evolution and Reengineering), pp. 193-204 · 2017

One of the first academic treatments of event sourcing as practiced in industry (grounded in the authors' experience at AFAS Software and validated through expert interviews), it catalogs the schema-evolution problem — the immutable log outlives the code that wrote it — and proposes an event-store upgrade framework combining upgrade operations with execution techniques and strategies (upcasters, lazy vs eager copy-and-transform conversion). Manikin inherits and arguably amplifies this burden: its log stores not just typed events but full read/write traces, all of which must survive schema change. Manikin's semantic rebase (re-executing messages under current code from a common ancestor) doubles as an 'upcast by replay' strategy, but the paper's evolution framework is something Manikin currently has no answer to and a paper should acknowledge.

Retro-λ: An Event-sourced Platform for Serverless Applications with Retroactive Computing Support

Meißner, Erb, Kargl, Tichy · DEBS 2018, pp. 76-87 · 2018

The Ulm line of work (Erb & Kargl's conceptual model for event-sourced graph computing, DEBS 2015; Chronograph, DEBS 2017; Retro-λ) is the closest academic system family to Manikin's forked worlds: Retro-λ lets programs rewrite or inject past events and replay them in isolated branched timelines to derive alternate presents, on an event-sourced serverless substrate. Both systems make history branching a first-class programming construct backed by replay. The difference is what branches are for: Retro-λ branches serve what-if analysis and are never merged back with conflict detection, whereas Manikin's merge uses per-dispatch read/write intersections to certify serializability and its pre/pst contracts re-validate during rebase — turning branches into a concurrency-control mechanism, not just an analysis tool.

IV.Specification and dependency tracking

15 Design by contract

where two decades of DbC research engineered protocols and copy-minimization to approximate a pre-state the mutable heap has already destroyed, Manikin simply never destroys it — the pre-state is a retained immutable world version, so even a multi-object old-state postcondition is just a read.

Manikin sits squarely in the Design-by-Contract lineage (the author cites Eiffel directly): every message dispatch executes a precondition stage (pre) and a postcondition stage (pst), and it shares the pre/post/old vocabulary of Eiffel, JML, Spec#, and Code Contracts as well as the library-embedded, no-compiler-changes stance of .NET Code Contracts. The decisive difference is that this entire literature assumes an in-place mutable heap, which generates its two hardest problems: the cost and fragility of old-state capture (Cheon-Leavens jmlc, Code Contracts' binary rewriter, Filliatre-Pascutto's prestate-copy optimization) and the question of when multi-object invariants may legitimately be broken (the Boogie pack/unpack methodology, Barnett-Naumann friendship, Leino-Muller dynamic contexts). Manikin dissolves both by construction: because worlds are persistent and every id:version survives, old() is a lookup rather than a copy, and a postcondition spanning several objects ("the sum of both balances is unchanged") is an ordinary query against the retained pre-dispatch world version — moreover the reads performed inside pre/pst are recorded into the same read set used for merge conflict detection, coupling contract monitoring to transactional dependency tracking in a way none of the surveyed systems do. A related-work section should also concede what Manikin lacks relative to this thread: no static modular verification (Spec#/Boogie), no contract inheritance or behavioral-subtyping rules (Eiffel, JML), no blame semantics for higher-order values (Findler-Felleisen), and no declared frame language — it observes exact write sets but has nothing like JML's assignable clauses to check them against, and its violations are detected at dispatch commit rather than prevented modularly. I found no prior work that uses versioned/persistent application state as the substrate for contract monitoring; the closest are copy-minimization (Filliatre-Pascutto) and instrumented recording of past memory states (E-ACSL's \at), both of which reconstruct a pre-state that the heap destroys.

Object-Oriented Software Construction (2nd edition)

Meyer · Prentice Hall (book) · 1997

The canonical Design-by-Contract text: Eiffel's require/ensure clauses, class invariants, and the old expression, all monitored at runtime. Manikin's pre and pst stages are Eiffel's contracts lifted to message dispatch over immutable worlds, and the author cites Eiffel as a direct influence. Eiffel implements old e by evaluating and copying the expression's value at routine entry (with well-known shallow-copy pitfalls) and scopes invariants to a single object, whereas Manikin's pst evaluates arbitrary expressions, including over multiple objects, against the retained previous world version with no copying. Manikin lacks Eiffel's contract-inheritance discipline (precondition weakening / postcondition strengthening under behavioral subtyping) and its mature tooling.

Applying "Design by Contract"

Meyer · IEEE Computer 25(10), pp. 40-51 · 1992

The article that named and popularized Design by Contract: contracts as mutual obligations between client and supplier, monitored at runtime for debugging and documentation. Manikin adopts this wholesale but embeds it in a transactional dispatch: a failed pre or pst aborts the entire message dispatch and leaves the world untouched, so contract failure is a clean rollback rather than an exception raised mid-mutation as in Eiffel's rescue mechanism. Meyer's contracts guard one receiver; Manikin's pst may quantify over the old and new state of several objects touched by the effect stage.

Preliminary design of JML: a behavioral interface specification language for Java

Leavens, Baker, Ruby · ACM SIGSOFT Software Engineering Notes 31(3), pp. 1-38 · 2006

JML brings behavioral interface specifications (requires/ensures, \old(), invariants, model fields, assignable clauses) to Java as annotation comments checked by external tools. Manikin shares the JVM setting and the old-state postcondition vocabulary, but its contracts are first-class code — the four stages of a Message value — rather than a specification layer bolted onto methods that mutate the heap in place. JML's \old() is confined to the method boundary and requires pre-state evaluation or copying; Manikin's versioned worlds give old-state access at any object granularity for free. JML is far richer as a specification language (model fields, frame clauses, specification inheritance), none of which Manikin offers.

A Runtime Assertion Checker for the Java Modeling Language (JML)

Cheon, Leavens · SERP 2002 (Proc. Int. Conf. on Software Engineering Research and Practice), pp. 322-328 · 2002

The jmlc compiler translates JML specifications into runtime checks, handling \old() by eagerly evaluating and saving pre-state values at method entry. This is the concrete engineering baseline for what Manikin gets structurally: because a dispatch's input world persists unchanged, pst simply reads any object's old version — no per-expression snapshotting, no aliasing hazards when \old captures a reference into a heap that then mutates. Manikin additionally records the reads performed inside pre/pst into the dispatch's read set, so contract evaluation participates in merge/serializability conflict detection, which no JML checker does.

The Spec# Programming System: An Overview

Barnett, Leino, Schulte · CASSIS 2004, LNCS 3362, pp. 49-69 (Springer, 2005) · 2004

Spec# extends C# with contracts, a compiler that emits runtime checks, and the Boogie static verifier, using an ownership-based methodology (expose blocks, pack/unpack) to define when object invariants may be temporarily broken during in-place mutation. Manikin shares the goal of contracts in a mainstream OO language with runtime enforcement, but sidesteps the broken-invariant window entirely: state transitions are pure functions from old world to new world, contracts are checked only at dispatch boundaries over immutable snapshots, and no other object can ever observe an intermediate state. Conversely, Manikin has nothing like Boogie — no static, modular proof of contracts, only monitoring.

Embedded contract languages

Fähndrich, Barnett, Logozzo · ACM SAC 2010, pp. 2103-2110 (industrial system: Microsoft .NET Code Contracts) · 2010

Code Contracts express contracts as ordinary method calls (Contract.Requires, Contract.Ensures, Contract.OldValue) in any .NET language, then use a CIL binary rewriter to hoist postconditions to method exits and snapshot old values. This is the closest industrial precedent for Manikin's embedding stance: contracts as library code in an unmodified host language. The difference is that Code Contracts needs post-compilation rewriting precisely because the host semantics give no staging and no pre-state; Manikin's Message structure makes the four stages explicit closures, and its persistent worlds supply OldValue without capture. Code Contracts also shipped an abstract-interpretation static checker (cccheck), which Manikin has no analogue of.

Contracts for higher-order functions

Findler, Felleisen · ICFP 2002, pp. 48-59 · 2002

Findler and Felleisen extend assertion-style contracts to first-class functions, introducing delayed checking via wrapper contracts and the blame theorem that assigns violations to the correct party. Manikin shares the view of contracts as first-class values in a functional host (Scala), but its dispatch surface is deliberately first-order — messages are immutable data sent to typed identities — so deferred higher-order checking never arises, and blame is trivially the offending dispatch recorded in the event log. Manikin has no blame calculus for contracts over function-typed state; conversely this line of work has no notion of old-state or multi-object postconditions, which are Manikin's center of gravity.

Verification of Object-Oriented Programs with Invariants

Barnett, DeLine, Fähndrich, Leino, Schulte · Journal of Object Technology 3(6), pp. 27-56 · 2004

The Boogie methodology: an explicit per-object validity state plus pack/unpack and ownership machinery to make precise when an object invariant must hold while the heap is mutated in place, including invariants over owned components. The entire apparatus answers a question Manikin makes vacuous — because a Manikin transition builds a new world version functionally, 'when does the invariant hold' collapses to 'at every committed dispatch', and there are no observable intermediate broken states. The trade is stark: this methodology supports sound modular static verification of invariants; Manikin only detects violations dynamically, at commit time.

Friends Need a Bit More: Maintaining Invariants Over Shared State

Barnett, Naumann · MPC 2004, LNCS 3125, pp. 54-84 · 2004

Extends ownership-based invariants to invariants linking objects in different ownership domains via a friendship protocol: granting clauses and update guards oblige each mutation of shared state to notify dependent friends. This is the closest prior treatment of Manikin's flagship contract — an invariant relating two peer objects, such as sum-of-two-account-balances conserved across a transfer. Manikin monitors exactly that as a pst reading both accounts' old and new versions, with zero protocol obligations threaded through the code; the price is that Manikin only detects the violation at dispatch commit, whereas friendship supports modular static prevention.

Object Invariants in Dynamic Contexts

Leino, Müller · ECOOP 2004, LNCS 3086, pp. 491-516 · 2004

Generalizes ownership-based invariant methodology to dynamic contexts: unbounded object sets whose membership changes, with ownership transfer, so an invariant may range over a whole context of objects. The multi-object scope parallels Manikin's cross-object postconditions, but here invariant scope must follow the ownership topology and mutation must respect the packing discipline. A Manikin pst may mention any objects addressable by identity, with those reads logged into the world's read set — no topology constraints — but Manikin gets only runtime detection over immutable snapshots, not the modular soundness argument this paper provides for in-place mutation.

Efficient Runtime Assertion Checking of Assignable Clauses with Datagroups

Lehner, Müller · FASE 2010, LNCS 6013, pp. 338-352 · 2010

The first algorithm to runtime-check JML assignable (frame) clauses in the presence of datagroups, intercepting heap writes via instrumentation and coping with datagroup membership that changes over time. This is the frame-monitoring problem that Manikin's worlds solve as a byproduct: every dispatch's exact write set (and read set) is recorded natively by the functional update discipline, with no bytecode instrumentation, and the same sets drive merge conflict detection. What Manikin lacks is the specification side: it observes frames but has no assignable-style declared frame to check the observed write set against.

Optimizing Prestate Copies in Runtime Verification of Function Postconditions

Filliâtre, Pascutto · RV 2022, LNCS 13498, pp. 85-104 · 2022

For Ortac, the runtime assertion checker for OCaml/Gospel, naive capture of old() state copies so much of the prestate that instrumented programs become impractical; the authors formalize a sound postcondition transformation that minimizes what must be copied and restore near-uninstrumented performance. This is the sharpest published evidence that old-state capture is a first-order cost of contract monitoring on mutable state — the exact cost Manikin eliminates, since persistent worlds retain every id:version and pst's old-state access is a lookup, not a copy (Manikin instead pays persistent-data-structure overhead on every update, contracts or not). In this survey it is also the nearest neighbor to Manikin's key claim; the only other close mechanism found is E-ACSL's \at(e,L) for C (Signoles, Kosmatov, Vorobyov, RV-CuBES 2017), which likewise must record past memory states by instrumentation rather than obtaining them from versioned state.

Added in the completeness pass

A Behavioral Notion of Subtyping

Liskov, Wing · ACM TOPLAS 16(6), pp. 1811–1841 · 1994

Introduces behavioral subtyping with the history constraint: a two-state property over any pair of object states ordered in time, constraining how objects may evolve (e.g., monotonicity), precisely to handle aliasing that pre/post rules alone miss. Manikin’s pst clauses are two-state properties in exactly this sense, evaluated over retained world versions; because Manikin has no subtype-driven message dispatch discipline yet, Liskov–Wing marks both the vocabulary its contracts already use and the inheritance rules a mature Manikin type hierarchy would owe its users.

16 Executable specifications and lightweight model checking

where Rebel asks the bank to write a second, checkable description of its products, Manikin instruments the production objects themselves — trading Rebel's solver-backed guarantees for the structural guarantee that the model can never drift from the code.

A related-work section should place Manikin at the "single artifact" end of the executable-specification spectrum. Classic specification languages — TLA+/PlusCal and Alloy — buy exhaustive or solver-backed analysis at the price of a model-code gap; the AWS CACM experience report documents that gap being managed entirely by hand, with specs maintained alongside unlinked C++/Java implementations. P, Stateright, and the Amazon S3 ShardStore work progressively close the gap by making the executable artifact itself the analyzed artifact, and Manikin pushes that move up to the application/business-logic layer: Eiffel-style pre/app/eff/pst contracts are stages of every production message, and Worlds — which already record complete read/write sets and full object version history for transactional merging — double as a light model-checking, mocking, and replay harness that is swapped in without touching business logic. The sharpest single comparison is Rebel, which comes from the same ING banking context Manikin's bank example mirrors and puts pre/postconditions on the same domain events; but Rebel and Rebel2 are external DSLs whose SMT-backed bounded checking analyzes specifications, with implementations generated or conformance-tested separately, whereas Manikin's "spec" is the production JVM code and checking is concrete execution over forked worlds. Relative to the QuickCheck line, Manikin internalizes the abstract state machine (preconditions/postconditions live in the message itself rather than in a parallel eqc_statem-style model) but supplies no generation, shrinking, or randomized parallel testing of its own — a property-based driver would have to be layered on top of forked Worlds. What Manikin lacks against nearly everything in this thread is verification power: no exhaustive or symbolic state-space exploration, no temporal/liveness properties, no small-scope solving for counterexamples; its checking is exactly as strong as the executions it drives.

Specifying Systems: The TLA+ Language and Tools for Hardware and Software Engineers

Lamport · Addison-Wesley (book) · 2002

The canonical TLA+ reference: systems are specified as state machines whose actions are relations over primed/unprimed variables, with invariants and temporal properties checked exhaustively on finite instances by the TLC model checker. Manikin's pre/app/pst stages structurally mirror TLA+'s enabling condition, next-state relation, and invariant, and both treat history as a sequence of states. The decisive difference is the model-code gap: a TLA+ spec is a separate untyped mathematical artifact, whereas Manikin's messages are the production code and a swapped-in checking World explores their behavior directly. Manikin lacks TLC's exhaustive enumeration, symmetry reduction, and liveness/temporal-logic checking.

The PlusCal Algorithm Language

Lamport · ICTAC 2009 (LNCS 5684, pp. 36-60) · 2009

PlusCal wraps TLA+ in an imperative, pseudocode-like algorithm language that is mechanically translated to TLA+ for checking with TLC. Its motivation — let engineers write imperative-looking logic while a formal substrate does the bookkeeping — is the same one behind Manikin's rejection of monads in favor of a ThreadLocal Environment that lets business logic read imperatively over pure Worlds. But PlusCal remains a modeling language with one-way translation away from the shipped system, whereas Manikin inverts the direction: the real JVM business logic is the sole artifact and the analyzable view is obtained by swapping the World implementation.

Alloy: a lightweight object modelling notation

Jackson · ACM TOSEM 11(2), pp. 256-290 · 2002

Alloy is the flagship of 'lightweight formal methods': a small relational notation for structural properties with fully automatic bounded analysis via SAT, finding instances and counterexamples within small scopes. Manikin shares the lightweight, developer-accessible ethos and the bet that shallow-but-automatic checking catches most defects. It differs in mechanism: Alloy analyzes declarative constraints symbolically and statically, while Manikin checks contracts by concretely executing real transitions in a checking World; Manikin cannot solve for counterexample instances, and Alloy models cannot run in production.

How Amazon Web Services Uses Formal Methods

Newcombe, Rath, Zhang, Munteanu, Brooker, Deardeuff · Communications of the ACM 58(4), pp. 66-73 · 2015

The landmark industrial report that TLA+/PlusCal pays off for engineers building transactional distributed services: AWS teams found subtle DynamoDB bugs requiring 35-step traces that testing had missed. It targets exactly Manikin's intended audience — working engineers on business-critical stateful systems — but it also documents the cost Manikin is designed to eliminate: AWS maintained specs by hand alongside C++/Java implementations with no mechanical link between them. Manikin removes the dual-artifact problem at the application-logic level, at the cost of giving up TLC's exhaustive search and liveness checking.

P: safe asynchronous event-driven programming

Desai, Gupta, Jackson, Qadeer, Rajamani, Zufferey · PLDI 2013 · 2013

P unifies modeling and programming: communicating state machines compile both to executable C (shipped in the Windows 8 USB driver stack) and to a systematic-exploration backend (Zing), so the checked model is the deployed program. This is the closest philosophical relative to Manikin's swap-in Worlds among the checking languages. P differs in domain and semantics — a standalone external DSL for asynchronous event-driven systems code — whereas Manikin is an embedded JVM DSL for transactional business objects with synchronous dispatch, four-stage contracts, and world fork/merge/rebase. P's scheduler-controlled systematic testing is also far more thorough than Manikin's light replay-based checking.

Stateright: a model checker for implementing distributed systems

Nadal · industrial open-source system (Rust, github.com/stateright) · 2018

Stateright is a Rust library in which an actor system written against its Model/Actor traits gets an embedded explicit-state model checker (with a linearizability tester and an interactive state-space UI) and can then run unmodified on a real network — precisely Manikin's 'swap the runtime, keep the logic' move, realized as exhaustive BFS exploration rather than Manikin's lighter world-forking. It targets distributed protocols (Paxos, Raft) with message-passing semantics, whereas Manikin targets transactional business objects with contracts; Stateright has no analogue of Manikin's read/write-set-based SSI-grade world merging, while its checker is substantially more thorough as a checker.

QuickCheck: a lightweight tool for random testing of Haskell programs

Claessen, Hughes · ICFP 2000 · 2000

The foundational property-based testing paper: executable specifications written as host-language properties, checked against randomly generated inputs with user-definable generators. Manikin shares the embedding of specification in the programming language and the reliance on execution rather than proof, but its pre/pst contracts are attached per-message and checked on every dispatch — in production or under a checking World — rather than driven by a random-input harness. Conversely Manikin provides no generation or shrinking; a QuickCheck-style driver over forked Worlds is the natural complement it lacks.

Testing telecoms software with Quviq QuickCheck

Arts, Hughes, Johansson, Wiger · ACM SIGPLAN Erlang Workshop 2006, pp. 2-10 · 2006

Introduces the commercial Erlang QuickCheck used on Ericsson's Megaco stack and the stateful (eqc_statem-style) discipline: the tester writes a separate abstract state machine with per-command preconditions and postconditions, and random command sequences are run against the real implementation. That abstract model duplicates exactly the pre/pst structure Manikin builds into the production message itself, so Manikin removes the parallel model — but at a price: it inherits only the contracts developers wrote into the code, whereas a separate QuickCheck model can serve as a deliberately simpler, independent oracle for third-party code that Manikin's discipline cannot cover.

Experiences with QuickCheck: Testing the Hard Stuff and Staying Sane

Hughes · A List of Successes That Can Change the World (Springer LNCS 9600), pp. 169-186 · 2016

Hughes's retrospective on fifteen years of industrial model-based QuickCheck (the briefing's short title 'Testing the hard stuff' verified as this chapter), covering stateful testing of C code for Volvo's AUTOSAR platform and race-condition detection by running command sequences in parallel and checking against a sequential model — linearizability testing by randomization. Manikin approaches the same concurrency-correctness problem constructively rather than by search: merge(w1,w2) checks precise read/write-set intersections, making serializability (including write skew) a deterministic application-level check instead of a property hunted by randomized parallel execution. Hughes's method, however, applies to arbitrary existing code, while Manikin's guarantees hold only for code written inside its object/message discipline.

Solving the bank with Rebel: on the design of the Rebel specification language and its application inside a bank

Stoel, van der Storm, Vinju, Bosman · ITSLE @ SPLASH 2016 (1st Industry Track on Software Language Engineering), pp. 13-20 · 2016

Rebel is a banking-domain specification DSL built with ING: financial products are specified as state machines over data with preconditions, postconditions, and synchronization constraints, checked by SMT-backed (Z3) bounded reachability and used to derive simulations and implementations. This is Manikin's nearest neighbor — same ING banking context, same account/transfer domain as Manikin's running example, same pre/postcondition-on-business-event structure — making it the mandatory comparison. Rebel is an external DSL whose solver analyzes specifications with code kept conformant separately; Manikin is an embedded DSL where the production code is the specification and checking is concrete execution. Manikin adds transactional world semantics (fork/merge/rebase, built-in event sourcing) that Rebel has no counterpart for, but lacks Rebel's symbolic reasoning and automated reachability checking.

Modeling with Mocking

Stoel, van der Storm, Vinju · IEEE ICST 2021, pp. 59-70 · 2021

The Rebel2 paper (the briefing's 'Rebel2 2021?' confirmed: this ICST 2021 paper presents Rebel2, evaluated on banking and automotive case studies). Rebel2 lets engineers write full, unabstracted state-machine specifications and recover tractable bounded model checking by 'mocking' and 'forgetting' parts of the specification during solving. The mock-to-check move directly parallels Manikin's swap-in Worlds — mock injection is one of Manikin's advertised swap-in capabilities — but Rebel2's mocks buy symbolic tractability inside a solver while Manikin's serve concrete test execution. Rebel2 still maintains a specification separate from production code; Manikin trades Rebel2's exhaustive bounded guarantees for zero model-code distance.

Using Lightweight Formal Methods to Validate a Key-Value Storage Node in Amazon S3

Bornholt, Joshi, Astrauskas, Cully, Kragl, Markle, Sauri, Schleit, Slatton, Tasiran, Van Geffen, Warfield · SOSP 2021 (best paper) · 2021

Reports validating ShardStore, a production S3 storage node in Rust, with executable reference models, property-based testing, and coverage-guided fuzzing — conformance checking maintained continuously by the product team as the code evolves. It shares Manikin's core thesis for this thread: pragmatic, automation-first checking should target the shipped code, not a separate proof artifact. It differs in that the S3 reference models are still separate oracles checked by randomized exploration, whereas Manikin bakes both the oracle (four-stage contracts) and the instrumentation (read/write-set tracking, full version history, event log) into the programming model itself; Manikin offers nothing like their coverage measurement or empirical soundness argument.

17 Provenance and incremental recomputation

where systems from self-adjusting computation to Salsa consume recorded read sets to decide what to recompute within a single evolving timeline, Manikin consumes the identical record to decide whether two timelines may lawfully become one.

A related-work section should present Manikin's worlds as a fine-grained dynamic provenance recorder — every dispatch logs exact read sets (including reads made inside pre/postconditions) and write sets over versioned identities — and then observe that the two literatures that own this machinery each consume it for a different purpose than Manikin does. Database provenance (Buneman's why/where, Green-Karvounarakis-Tannen semirings, the Cheney-Chiticariu-Tan taxonomy, W3C PROV) supplies the vocabulary — Manikin's read sets are why-provenance, its event log is how-provenance, its world history maps mechanically onto PROV entities/activities — but consumes provenance for explanation, annotation, and trust, not for admission control between divergent states. Incremental computation (Pugh-Teitelbaum memoization, Acar's self-adjusting computation, Adapton, Salsa/rust-analyzer, and above all the rebuilder abstraction of Build Systems à la Carte) consumes recorded dynamic dependencies to decide what to re-execute, which is exactly Manikin's rebase; the section should say plainly that merge is a verifying-trace check and rebase is the rebuild path, and that a successful rebase guaranteeing a subsequent merge mirrors a rebuilder restoring store consistency. What Manikin adds over that entire thread is pointing the same dependency record at a question no single-timeline incremental system asks: whether two forked histories may be combined, with read/write-set intersection giving application-level serializability that catches write skew. The nearest true precedent for provenance-driven merge decisions is collaborative data sharing (ORCHESTRA's trust-filtered update exchange, Taylor-Ives reconciliation), which however decides per-tuple under trust priorities and tolerates permanent divergence rather than guaranteeing a serializable result. Honesty requires conceding what Manikin lacks from this thread: no early cutoff, memoization, or demand-driven reuse, so rebase replays every message in full where SAC, Adapton, and Salsa would skip untouched work — a gap its own recorded read sets make straightforwardly closable.

Why and Where: A Characterization of Data Provenance

Buneman, Khanna, Tan · ICDT 2001 (LNCS 1973, Springer, pp. 316-330) · 2001

Introduces the why-provenance / where-provenance distinction: the set of input tuples that witness an output versus the exact source locations a value was copied from. Manikin's per-dispatch read set is precisely a why-provenance (lineage) record at object-version granularity — the set of id:version pairs, including reads made inside pre and pst conditions, that justify each write and return value. Buneman et al. derive provenance syntactically/semantically from declarative queries over hierarchical data, whereas Manikin records it dynamically from imperative-looking message dispatches and consumes it operationally (merge admission) rather than for explanation. Manikin lacks where-provenance: it cannot say which field of which object a value was copied from, only which objects were read.

Provenance Semirings

Green, Karvounarakis, Tannen · PODS 2007 (ACM, pp. 31-40) · 2007

Annotates tuples with elements of a commutative semiring (most generally polynomials N[X]) so that query answers carry an algebraic expression describing exactly how they were derived, uniformly capturing lineage, why-provenance, trust, and incremental update propagation. Shared with Manikin is the thesis that recorded derivation structure enables downstream decisions; different is that semiring provenance is symbolic and compositional over relational operators, so the effect of changing an input annotation can be computed by re-evaluating a polynomial without re-running the query. Manikin's provenance is an unstructured dynamic trace: to learn how a changed ancestor affects a message it must semantically re-execute it (rebase). Manikin adds contract checking (pre/pst) and serializability-grade merge tests, which have no analog in the semiring framework.

Provenance in Databases: Why, How, and Where

Cheney, Chiticariu, Tan · Foundations and Trends in Databases 1(4), pp. 379-474, now publishers · 2009

The standard survey organizing database provenance into why- (witnesses), how- (derivation structure), and where- (copying) provenance, and cataloguing applications including view maintenance, updates, and debugging. Useful to a Manikin related-work section chiefly as the taxonomy anchor: Manikin's read/write sets are why-provenance, and its append-only event log of successful dispatches is a how-provenance of application state. The survey's application list (explanation, annotation, view update) conspicuously does not include concurrency control or merging of divergent states, which is exactly the gap Manikin's merge/rebase occupies. Conversely Manikin offers none of the query-rewriting or minimal-witness machinery the surveyed systems provide.

PROV-DM: The PROV Data Model

Moreau, Missier (eds.) · W3C Recommendation, 30 April 2013 · 2013

The W3C standard interchange model for provenance: entities, activities, and agents linked by usage, generation, and derivation relations. A Manikin world history maps onto a PROV instance almost mechanically — object versions are entities, message dispatches are activities, read-set entries are 'used' edges, write-set entries are 'wasGeneratedBy' edges, and successive versions of an id are 'wasDerivedFrom' chains. The decisive difference is that PROV is descriptive of a computation, not operational within it: the companion PROV-CONSTRAINTS recommendation only validates the internal consistency of a provenance document, and nothing in the PROV family gates the execution being described, whereas Manikin's identical graph is the operational input to merge (set intersection) and rebase (replay). Manikin lacks PROV's interoperability, agent/attribution modeling, and any export path; emitting PROV from world logs would be a trivial and worthwhile bridge to claim.

Adaptive Functional Programming

Acar, Blelloch, Harper · POPL 2002 (ACM, pp. 247-259); expanded in Acar's CMU PhD thesis 'Self-Adjusting Computation' (CMU-CS-05-129, 2005) and TOPLAS 28(6), 2006 · 2002

Founds self-adjusting computation: executions build a dynamic dependence graph of modifiable references, and a change-propagation algorithm re-executes only the sub-computations whose recorded reads are affected by an input change, with correctness argued via trace stability (the thesis adds memoization and the full trace-based theory). This is the same architecture as Manikin's rebase — recorded dynamic reads determine what must be re-run against a changed store — but at very different granularity: SAC re-executes sub-expressions within a single computation and reuses unaffected fragments, while Manikin replays entire messages from the common ancestor and reuses nothing. Manikin adds what SAC lacks entirely: multiple concurrently forked stores, a merge criterion over read/write sets, and pre/postcondition contracts re-checked on replay. Manikin lacks SAC's fine-grained reuse, which is why rebase is its slow path rather than an O(affected) operation.

Incremental Computation via Function Caching

Pugh, Teitelbaum · POPL 1989 (ACM, pp. 315-328) · 1989

The seminal memoization approach to incremental computation: cache function results keyed by arguments (with hash-consing for fast equality) and reuse a cached result whenever the arguments are unchanged, making re-execution after small input changes cheap. It is the direct ancestor of the dependency-fingerprint checks in later build systems and query frameworks. Manikin's rebase currently lacks even this 1989-level optimization: it re-executes every message from the common ancestor rather than skipping dispatches whose recorded read sets are disjoint from the other world's writes — a reuse opportunity its own provenance record already makes checkable in O(set intersection). Citing Pugh and Teitelbaum lets the paper acknowledge this as known future work rather than a novelty claim.

Adapton: Composable, Demand-Driven Incremental Computation

Hammer, Khoo, Hicks, Foster · PLDI 2014 (ACM, pp. 156-166) · 2014

Generalizes self-adjusting computation with a demanded computation graph that is bidirectional (dirtying flows from changed inputs, re-evaluation flows from demanded outputs), giving lazy, compositional incremental computation whose results can be reused across differing contexts; the follow-on 'nominal' Adapton keys cached computations by programmer-chosen first-class names. The nominal-names idea is the closest analog in the incremental literature to Manikin's typed identities Id[O], which likewise give stable, programmer-visible names that determine where state versions live and where dependencies attach. Adapton, however, incrementalizes recomputation over one mutating input store, while Manikin's identities index versions across many forked worlds and feed a merge test rather than a memo-match. Manikin lacks Adapton's demand-driven laziness — every dispatched message runs eagerly — and Adapton lacks any notion of transactions, contracts, or reconciling divergent stores.

Build Systems à la Carte

Mokhov, Mitchell, Peyton Jones · ICFP 2018 (PACMPL 2(ICFP), article 79) · 2018

Decomposes build systems (Make, Excel, Shake, Bazel, Nix) into an orthogonal scheduler plus a rebuilder, where rebuilders — dirty bits, verifying traces, constructive traces — consult recorded dynamic dependencies to decide whether a stored result may be reused or must be recomputed. This is the cleanest published frame for Manikin's two-path design: merge is a verifying-trace check (do the recorded reads of one world intersect the writes of the other?) and rebase is the rebuild path taken when verification fails, with the paper's guarantee that a successful rebase makes the subsequent merge succeed mirroring a rebuilder restoring consistency. The difference is that build systems rebuild toward one consistent store from changed inputs, whereas Manikin reconciles two divergent stores and additionally checks write/write intersections to obtain serializability, a property build systems never need. Manikin lacks the early-cutoff and constructive-trace (cloud cache) reuse the paper catalogues, which would let rebase skip messages whose read sets are untouched.

Salsa: a generic framework for on-demand, incrementalized computation (used in rust-analyzer and modeled on rustc's red-green query system)

Matsakis, Kladov, and the salsa-rs contributors · industrial system (open-source Rust framework; salsa-rs/salsa on GitHub) · 2018

Salsa structures a program as memoized queries whose runtime-recorded dependency edges drive the red-green algorithm: after an input changes, a query re-executes only if some recorded dependency actually produced a different value, with early cutoff ('backdating') stopping propagation when a recomputed value is equal to the old one, plus revision counters and durability levels to cheapen validation. It shares with Manikin the disciplines of dynamic dependency recording behind a pure-function contract (Salsa queries must be deterministic, like Manikin's pure app stage) and identity-keyed state. But Salsa maintains a single input timeline mutated in place under one writer, so its provenance answers 'what must be recomputed?', never 'may these two histories be combined?'. Manikin adds forked worlds with read/write-set merge and write-skew detection; it lacks Salsa's early cutoff, demand-driven evaluation, and durability-tiered validation, all of which would directly accelerate rebase.

Update Exchange with Mappings and Provenance

Green, Karvounarakis, Ives, Tannen · VLDB 2007 (pp. 675-686) · 2007

The ORCHESTRA collaborative data sharing system propagates updates between peer databases along schema mappings while materializing semiring provenance for every propagated tuple, and — the key precedent — peers evaluate trust policies over that provenance to decide which incoming updates to accept. This is the most direct prior art for Manikin's central move of using a provenance record to make merge decisions between divergent replicas. The mechanisms differ sharply: ORCHESTRA's acceptance is per-tuple, policy-based, and deliberately tolerates permanent divergence between peers, whereas Manikin's merge is an all-or-nothing intersection test over exact read/write sets that either yields a serializable combined world or falls back to semantic rebase. Manikin also checks read/write conflicts (catching write skew), which ORCHESTRA's trust conditions never consider; ORCHESTRA in turn handles schema heterogeneity, which Manikin does not attempt.

Reconciling while Tolerating Disagreement in Collaborative Data Sharing

Taylor, Ives · SIGMOD 2006 (ACM, pp. 13-24) · 2006

Defines reconciliation for peers that independently edit shared data: updates are grouped into transactions with recorded antecedent conditions, and each peer's reconciliation accepts the maximal set of non-conflicting transactions under its own priority assignments, explicitly permitting peers to disagree forever on contested values. Like Manikin it detects conflicts at transaction granularity between divergent replicas and replays/accepts whole transactions, not individual writes. It differs in resolution semantics: conflicts are settled by per-peer trust priorities and divergence is a feature, while Manikin refuses any merge that is not serializable and uses rebase (semantic replay from the common ancestor) as the only conflict-resolution mechanism. Manikin's tracking is also strictly finer on the read side — condition reads inside pre/pst enter the conflict test, so write skew is caught, which antecedent-based reconciliation does not guarantee.

All You Ever Wanted to Know about Dynamic Taint Analysis and Forward Symbolic Execution (but Might Have Been Afraid to Ask)

Schwartz, Avgerinos, Brumley · IEEE Symposium on Security and Privacy 2010 (pp. 317-331) · 2010

Formalizes dynamic taint analysis as an instrumented operational semantics that propagates labels alongside ordinary evaluation, and systematizes its failure modes: under-tainting (missed implicit flows through control dependence) and over-tainting. Manikin's world dispatch is likewise an instrumented semantics — every read and write is forced through the World interface, which records labels (id:version access facts) as execution proceeds. The contrast favors Manikin's design point: because objects are reachable only via identities dispatched through the world, its read/write record is complete-by-construction at object granularity, sidestepping the under-tainting problem that plagues binary-level taint, at the cost of far coarser granularity (whole objects, not bytes or fields) and a cooperative rather than adversarial setting. Taint systems consume labels to enforce information-flow policies; Manikin consumes them for merge admission and replay — same machinery, different verdict.

Differential Dataflow

McSherry, Murray, Isaacs, Isard · CIDR 2013 · 2013

Generalizes incremental computation to arbitrarily nested iteration by indexing collection differences over a partially ordered set of versions, so updates flow as differences rather than recomputation (implemented in Naiad and its Rust successors). It is the systems-side apex of the incremental lineage this thread otherwise covers from the PL side, and its partially-ordered versions are the closest incremental-computation analogue to Manikin’s world DAG; differential dataflow propagates deltas through one dataflow, while Manikin asks the version poset a question differential dataflow never poses — whether two incomparable versions can be joined serializably.

18 The novelty question, answered adversarially

A dedicated agent was instructed to refute the novelty claim — to find any prior system combining ingredients (a), (b), and (c). Its verdict, after verification:

Worlds already guards commit with a read-set serializability check and Kung–Robinson supplied Manikin's merge rule in 1981; Manikin's contribution is to make sibling worlds merge and rebase like git branches while design-by-contract conditions vote in the serializability check.

Verdict

An adversarial reading finds every individual ingredient of Manikin anticipated, and the combination claim survives only in a narrowed form. The nearest neighbor is VPRI's Worlds (Warth et al., ECOOP 2011) — which Manikin itself cites — and it is closer than the fact sheet implies: the ECOOP paper's commit operation is explicitly "guarded by a serializability check" (a child world may commit only if nothing it read was modified in the parent since sprouting, with read/write sets propagated upward), so fork-able state scopes with read-set-checked commits embedded in a mainstream language (JavaScript, Squeak) existed by 2011. Manikin's merge rule itself — succeed iff write/write and read/write intersections are empty — is Kung–Robinson optimistic validation (TODS 1981) lifted to a symmetric two-way merge, and the "precise, not approximate SSI" refinement was already realized at the database level by PSSI (ICDE 2011); tracking the reads made by declarative conditions in the transaction's read set appears in Harris and Peyton Jones's STM invariants (TRANSACT 2006); versioned transactional object graphs embedded in Java date to JVSTM (2006) and commit-time conflict detection over language-level object graphs to GemStone/S (industrially, late 1980s). Git-like branch/merge/rebase of application state is well-trodden by Concurrent Revisions, TARDiS, Irmin, Dolt, and CoreObject — but notably every one of these resolves merges structurally or with type/application-supplied merge functions, deliberately abandoning serializability, whereas Worlds, which keeps serializability, has only linear child-to-parent commit with no sibling merge and no rebase. What no verified prior system provides is exactly that residue: symmetric merge plus semantic rebase-by-replay of forked worlds where the serializability check consumes read sets that include design-by-contract pre/postcondition reads (making write skew against a multi-object invariant a detectable merge conflict), packaged as a 4-stage message discipline with swap-in world implementations for event sourcing, mocking, and distribution. A related-work section must therefore not claim novelty for branchable state, for the merge criterion, or for contracts, but only for this synthesis — and should concede that Manikin's disjointness test is more conservative than PSSI-style cycle detection and that it lacks the deterministic merge functions, selective undo, and collaboration support of the branch-and-merge line.

CoreObject: distributed version control and object persistence framework

Wasylishen, Mathé · open-source system (Étoilé project), coreobject.org · 2014

A version-controlled object database for Objective-C object graphs supporting branching, full history tracking, selective undo, semantic (schema-aware diff/merge) merging, real-time collaborative editing, and a transaction API for viewing snapshots in memory — the closest verified 'git for object graphs' system, i.e., a direct prior instance of (a) at object-graph granularity. Its merges are property-level diff-based reconciliations with conflict surfacing, not a serializability check over tracked read/write sets, and it has no design-by-contract stages and no isolation guarantee across branches. Manikin conversely lacks CoreObject's selective undo and collaborative-editing machinery.

Dolt: Git for Data

Sehn and the DoltHub engineering team · industrial system (DoltHub Inc.) · 2019

A MySQL-compatible SQL database offering complete git semantics — branch, merge, rebase, diff, clone, push/pull — over Prolly-tree storage, with conflicts detected cell-wise; the most prominent industrial embodiment of git-for-application-state. Its merges are structural three-way reconciliations of table cells against the common ancestor, so two branches that each read what the other wrote merge without complaint even when the combined result is not serializable — precisely the semantic dependency information Manikin's read/write sets add. Dolt versions durable tables rather than in-memory object graphs and has no message contracts; Manikin lacks Dolt's storage-level diff efficiency and its collaboration ecosystem.

Datomic: The Database as a Value

Hickey and the Cognitect team · industrial system (Relevance/Metadata, later Cognitect) · 2012

An immutable database that only accretes facts (datoms), keeps the entire history queryable via as-of and history views, treats the transaction log as a built-in event source, and provides speculative forked database values through db.with(tx) — anticipating Manikin's immutable versioned worlds, event log, and speculative execution from within a JVM language. Datomic sidesteps the merge problem entirely: speculative values cannot be merged back, and all real writes serialize through a single transactor, so no read/write-set validation or rebase exists. Integrity is enforced by transaction functions that can abort (compare-and-swap style preconditions), which is coarser than Manikin's per-message pre/app/eff/pst discipline with multi-object old-state postconditions.

The GemStone Object Database Management System

Butterworth, Otis, Stein · Communications of the ACM 34(10), pp. 64-77; GemStone/S industrial OODB · 1991

GemStone/S is a Smalltalk object server, in production since the late 1980s, with optimistic transactions over shared persistent object graphs: sessions read and write objects freely and the server detects conflicts at commit time by intersecting sessions' object-level write sets, dependency lists, and locks (per the GS/64 Programming Guide) — commit-time set-based conflict detection over language-level object graphs, industrially, decades before Manikin. Its default detection is write-write plus write-dependency (read sets are tracked, but read/write conflicts are checked essentially only for indexed collections, so general write skew is admitted by default), there is a single shared head rather than a branch DAG — no named worlds, no sibling merge, no rebase — and no contract stages exist. Manikin can be framed as GemStone-style optimistic object transactions upgraded to precise serializability and git-like multi-world structure.

19 What a paper must concede

Aggregated from the eighteen threads, these are the concessions an honest paper makes up front — each one surfaced by the survey itself, with the literature that names the standard to meet.

  • No formal semantics. Worlds formalizes lookup; Burckhardt & Leijen give a revision calculus with a determinacy proof; transactors have the τ-calculus; homotopical patch theory is mechanized. Manikin has only an executable semantics — the ESOP 2011 revision calculus is the model to formalize merge/rebase against.
  • The merge criterion is conservative. Complete read/write disjointness is stricter than serializability itself. PSSI’s exact cycle detection is the precision endpoint; Manikin eliminates PostgreSQL-style granularity false positives but introduces criterion false positives, and compensates with rebase rather than a sharper test. This trade must be stated, not hidden.
  • No determinism. Concurrent Revisions, DPJ, LVars, and Dthreads guarantee deterministic outcomes; Manikin’s merge results depend on fork/merge order and timing. It trades determinism for serializability plus contracts — the opposite bet, and a fair reviewer will want it named.
  • Rebase replays everything. Self-adjusting computation, Adapton, Salsa, and Build Systems à la Carte all skip work whose recorded dependencies are untouched; Manikin’s own read sets would support exactly that early cutoff (even Pugh & Teitelbaum’s 1989 memoization), but the implementation replays every message from the common ancestor.
  • Safety is architectural, not static. Nothing in the JVM type system stops the ThreadLocal Environment or an object reference from escaping its world’s dynamic extent — no runST-style parametricity fence, no Effekt-style second-class capabilities. Scala capture checking (Capturing Types, TOPLAS 2023) shows what a statically safe frontend would look like.
  • No availability story. A Manikin merge can fail where a CRDT/MRDT merge cannot; there is no anti-entropy, no partition tolerance, no peer-to-peer sync. Distribution is delegated wholesale to a serializable store (CockroachDB), inheriting its coordination costs.
  • Contract machinery is monitoring-only. No static verification (Spec#/Boogie), no contract inheritance or behavioral-subtyping rules (Eiffel, JML, Liskov–Wing), no declared frames to check observed write sets against, no blame calculus.
  • The log outlives the code. Overeem et al. show schema evolution dominates event-sourcing maintenance; Manikin’s log stores full read/write traces, amplifying the burden, and rebase-as-upcast is a sketch, not an answer.
  • Phantoms are only partially handled. Read sets are keyed by object identity; predicate-level anomalies over collections are caught only when the collection is itself a versioned worldly object.
  • No performance evaluation. Every systems thread in this survey (TL2, Grace, TARDiS, ForkBase, Block-STM, Orleans) carries an evaluation; Manikin competes on semantics and currently offers no comparable measurement.
